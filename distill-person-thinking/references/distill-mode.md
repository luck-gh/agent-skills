# 蒸馏模式

## 开始条件

明确人物身份后立即开始.只有同名人物无法区分,用户要求的范围会显著改变结果,或非公众人物缺少授权材料时才提问.默认蒸馏人物在公开材料中反复体现的思维模型和决策方法,不默认模仿语气.

## 1. 核对已有本地模型

1. 按入口的人物身份规则查找已有核心文件.内置核对 person_id,person 和 aliases,外部按现有身份规则;匹配成功时沿用已有身份,具体模型 ID 和文件精确位置,不由新译名另建人物.
2. 只有确认没有已有匹配且不存在身份或文件名冲突时才分配新标识.维护内置时使用稳定英文 person_id 与 `思维模型_<常用姓名>.md`,常用姓名按入口规则选择通行中文名并将文件名中点转换为下划线;外部新成果继续使用未占用的 `<slug>.md`,不批量改名或给既有外部文件补字段.
3. 已存在时读取该人物的完整模型文件,把本次工作视为增量更新.不要因新材料无条件重写全部结论.
4. 普通运行中外部无匹配而内置有该人物时,可把内置核心及来源作为研究起点,新成果写入外部根.明确维护内置集合时按入口的维护授权更新原文件及索引;两种路径都保留已支持的模型身份与来源绑定.
5. 从内置生成外部版本时,将本次采用的已核验来源归纳整理到外部根的 `sources/<slug>_Sxx.md`,同步核心相对链接与笔记回链,保留原 URL,阅读范围和来源编号.不得原样带入内置文件名链接,跨根引用内置笔记或复制无关材料;不重复研究已充分核验的部分.

## 2. 发现已有公开 Skill

先通过可用的网页搜索能力查找该人物是否已被公开蒸馏.组合人物本名,常用别名和英文名,使用 `SKILL.md`,`Agent Skill`,`perspective`,`thinking`,`mental model`,`playbook` 等限定词搜索 GitHub,公开 Skill 仓库和公开索引.

对每个候选实际打开仓库和 `SKILL.md`,不要依据搜索摘要判断.记录:

- 仓库和精确文件 URL.
- 作者,license,查看日期和可辨认的版本或 commit.
- 它声明的模型,来源和适用范围.
- 是否给出可核验的一手来源.

已有 Skill 属于发现线索.没有原始出处的结论不能直接进入人物核心模型;有出处的结论回到原始来源复核.不要自动 clone,安装,执行或整段复制候选 Skill.

先查内置模型索引中的固定候选,已有线索可减少重复发现,不能省略原始证据核验.上游有新版时固定本次实际读取的版本,不将旧版与新版的来源静默混合.

## 3. 搜索人物原始材料

在已有 Skill 线索之外独立研究,避免循环引用.优先顺序:

1. 本人著作,论文,博客,公开信,演讲原文和完整访谈.
2. 经身份核验的官方社交账号及其原始帖子或 thread.
3. 可核对上下文的决策记录,产品发布,听证,问答和复盘.
4. 可信媒体的完整访谈或高质量传记.
5. 二手评论只用于发现争议,反例和待核实线索.

社交平台搜索同时覆盖人物常用平台,姓名变体和关键主题.确认账号与本人关联后再采用内容;无法确认时标为不确定.保留发布日期,直接 URL 和必要上下文,不要把转发,截屏或摘录页误当本人原话.

用户明确只用其提供且有权使用的材料时,不联网,同样保留出处和证据门槛.在线研究无法打开实际来源时停止在线分支并说明缺口,不得用模型训练记忆补齐来源.

## 4. 从证据提炼方法

从材料中提取候选模型,每条至少包含:

- 候选判断或方法.
- 出现场景和日期.
- 人物实际采取的动作或明确解释.
- 支持来源编号.
- 反例,观点变化或适用边界.
- 当前置信度.

一个结论满足下列任一条件后才可升级为核心模型:

- 在两个不同场景中由独立的一手材料重复体现.
- 同时存在一项可观察的决策或行动记录,以及一项本人对该方法的直接解释.

只满足一次陈述的内容降级为候选启发式.通用常识,粉丝概括,无出处金句和无法区分于其他人的观点不进入核心模型.

## 5. 处理冲突和变化

- 时间变化: 标注早期和近期立场,不要静态平均.
- 场景差异: 分别记录适用条件,不要强行统一.
- 言行冲突: 同时保留说法和可观察行动,降低置信度.
- 资料不足: 明确列为未知,不以流畅叙述掩盖缺口.

## 6. 生成和验证

按照[人物模型合同](profile-contract.md)生成一个完整人物核心文件,将已核验的材料吸收为判断框架,步骤,信号与局限.对本次采用的外部材料,按[来源蒸馏规范](source-distillation.md)生成有具体方法,案例和证据边界的本地笔记,核心 Sources 简短链接这些笔记.不保存网页转录或研究日志;不能只把网页变成本地文件而不提炼方法,也不能把核心执行所需的规则留在附件里.

在任何写入前,对候选执行以下行为检查:

1. 用至少两个该人物有公开立场或决策记录的问题回放模型,检查推导方向是否一致.
2. 用一个人物未明确讨论但邻近的问题检查外推,输出必须标明推断和不确定性.
3. 用一个与人物无关的普通请求检查边界,该人物模型不应被调用.
4. 检查每个核心模型是否有适用条件,执行步骤,证据编号和失效条件.
5. 按模型标签契约核对检索字段,正文模型 ID 和适用范围.用一个相近任务和一个排除场景检查标签不会把不适用模型列为可用.
6. 对照原文检查来源笔记中的情境,公开解释/行动和当前归纳,核实未把推断写成本人观点,未靠同一原文拆分制造独立证据.确认笔记能解释具体取舍,且核心已吸收关键方法,反例及改判条件.
7. 分别验证只读核心的普通任务与需要一个具体案例的深入任务:前者可独立使用,后者仅沿相关 Sxx 链接读取,不遍历 sources 或默认重新联网.来源不可访问或笔记写入失败时如实保留缺口,不生成空壳或宣称本次完成.

这些检查可以作为实现者回放,不得标成独立评测.回放题尽量不重复候选文件的示例答案;不得靠声称像本人或上游保真分数替代证据核对.

验证失败时在候选中删除或降级薄弱结论,不要通过增加更强语气掩盖问题.通过后按来源蒸馏规范保存,处理失败并回读核心与本次笔记;文件仅存在或工具仅报告写入成功都不构成完成证据.不绑定用于蒸馏的模型版本,不把静态通过当作其他模型使用效果已验证.

## 7. 报告结果

报告创建或更新的核心和来源笔记精确文件,核心模型数量,研究截止日期,主要来源类型,实际阅读范围,低置信度项和未解决缺口.说明哪些判断由材料支持,哪些属于当前推断,不要用"已还原本人","数字分身"或类似结论描述结果.
