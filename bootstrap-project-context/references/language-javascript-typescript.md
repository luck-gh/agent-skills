# JavaScript 与 TypeScript 防御边界

仅为 JavaScript 或 TypeScript 组件建立或校准开发规范时读取.先核对浏览器/服务端宿主,实际编译配置和已有数据校验方案;JavaScript 不套用 TypeScript 专有配置.

- 网络 JSON,存储内容,消息和第三方 SDK 结果在可信内部模型形成之前按运行时契约解析.已有 schema 或框架校验覆盖时复用;不因为缺少 Zod 就强制新增它,也不同时维护重复 schema 和手写判型.
- TypeScript 的类型断言 `as`,非空断言 `!` 和泛型参数不能验证运行时数据.未验证值保持未知输入语义,校验成功后内部按类型使用;纯 JavaScript 依靠同样的入口契约,不靠注释假定外部可信.
- 项目若已有 Zod 等工具,按既有错误通道选解析异常或显式成功/失败结果,调用方必须处理失败.不把安全解析失败改写为 `{}`,`[]` 或默认成功对象,不以 `any` 或双重断言跳过检查.
- 在能处理或转换外部失败的层接住异常或 Promise rejection,保留原因和操作上下文,不要在每层 `catch` 后继续.只在已知外部 API 可能抛非 Error 值时规范化它,不把这个情况推广成内部通用包装.
- `?.` 和 `??` 仅表达真实可选值与已约定默认语义,不能掩盖必需字段缺失.异步取消,资源释放与迟到结果的归属按实际宿主保证;静态类型不能证明任务已取消或对象仍有效.
- 以真实坏输入和异步失败验证边界,按项目已有入口做类型/构建与相关行为检查;类型检查通过不等于用户交互验收通过.
