# 项目上下文基线契约

仅在项目根级指令入口没有路径冲突,且不存在 `AGENTS.override.md` 时使用本契约.单一事实源,证据,隐私与文档职责适用于全部模式;下方固定四文件的状态判定和整组写入流程仅用于初始化或补齐.显式校准不因基线完整而退出,也不自动补建基线,只预检和更新已授权的文档集合.

## 目标与基线状态

目标文档集固定由以下文件组成:

- 根目录 `AGENTS.md`
- `docs/PLAN.md`
- `docs/FEATURES.md`
- `docs/EXPERIENCE.md`

检查 `docs` 及四个目标路径的原始名称和原始路径类型.`docs` 必须是缺失或普通目录;每个目标文档必须是缺失或普通文件.任何大小写变体,目录占位,符号链接,Junction,reparse point 或 broken path 都是冲突.

在写入前读取所有已有目标文档并判定唯一状态:

- 完整:四份普通文件均存在且非空,各自承担本契约定义的职责,`AGENTS.md` 提供简短开发流程,三份基线及适用专项文档的读取与更新路由,其中的指针可解析.没有独立专项文档本身不构成缺失.保持所有文件不变并报告 no-op.
- 可补齐:目标缺失,为空,或者现有内容与对应职责兼容但不完整.允许创建缺失目标,填充空文件,或只补充缺失职责.
- 冲突:`docs` 或目标路径类型不安全,文档承担不同职责,已有目标或约束相互冲突,或者无法在保留有效内容的前提下安全合并.在任何写入前停止并报告.

保留 `docs` 中的所有非目标文件和目标文档中仍然有效的信息,不要求保留每段历史原文.不得重命名,移动,删除文件或整篇替换来规避冲突.获准收敛文档时,可按下方增长控制规则合并与删减正文,但不能消除尚未解决的冲突.现有目标文档的当前状态被更新且可验证的证据明确推翻时,不属于语义冲突;应在其原职责内最小纠正,并在交付中说明.涉及产品意图或证据不足时不得猜测哪一项过时.

## 单一事实源与信息路由

每项信息只有一个权威位置.一次发现可以拆成不同职责的多个事实,但同一个事实不得跨文档复制.已有项目文档,任务系统,配置或脚本已经权威定义内容时,保留其归属并建立指针,不要为了填满四份文档而搬运正文.

验证信息需要按职责拆分:构建或测试配置拥有验证定义和行为,`AGENTS.md` 只保存已确认的稳定入口,`FEATURES.md` 只保存支撑已入档能力所必需的验证结论与证据指针,不收集每轮结果.稳定入口必须是项目已有的命名脚本,任务,构建目标或权威说明指定的规范入口;不得把内部展开命令或本轮临时命令提升为稳定入口.尚未建立入口时如实标记,不自动制造建立入口的计划.专项验证的保留方式见下方 FEATURES 契约;脚本或测试文件存在只能说明验证定义,不能冒充实际成功执行的证据.

| 权威位置 | 保存内容 | 不保存内容 |
| --- | --- | --- |
| `AGENTS.md` | 稳定的项目开发规则,按任务读取文档的条件,验证入口和收口流程 | 临时状态,项目摘要,详细计划或历史结果 |
| `docs/PLAN.md` | 项目级目标,约束,关键决策,当前阶段,用户讨论确认或同意入档的后续计划,相关依赖,风险和开放问题 | 临时实施步骤,未获同意入档的局部任务,已完成计划,已验证能力的重复说明或已有任务系统的完整镜像 |
| `docs/FEATURES.md` | 有实现与成功验证依据的当前主要能力,适用范围,关键限制及必要导航 | 全部功能明细,逐轮测试报告,计划,推测或未经验证的能力声明 |
| `docs/EXPERIENCE.md` | 经实际实施或验证证实,且可在本项目复用的经验 | 一般建议,任务流水账或未经验证的印象 |
| 已有权威来源 | 专项架构,协议,任务详情,自动生成状态及其他已被项目明确拥有的事实 | 四份基线文档中的重复副本 |

如果项目已经明确使用 issue tracker,任务目录或其他任务真源,`PLAN.md` 只保存项目级方向,里程碑,依赖和风险,并指向任务真源;不得复制完整 backlog 或维护第二套任务状态.如果没有任务真源,`PLAN.md` 才拥有按下方条件确认入档的后续计划,不收录 Agent 为当前执行临时拆出的步骤.

四份文档都是可持续维护的项目事实,不是单次会话 handoff.不得保存“停在第几步”,当前终端进程,本轮临时文件或只对当前 Agent 可见的记忆.

## 更新条件与免更新范围

建立或补齐基线时仍按四文件契约记录最小项目事实;以下条件决定后续维护,不免除首次建档.用户显式要求校准,纠正或整理文档时按授权处理,但不为产生改动而制造新事实,也不把校准建议擅自改写成已确认计划.

PLAN 的新增与调整由计划讨论和用户同意触发,不是由代码变动量或每轮对话触发:

1. 用户讨论并明确后续要做的计划,范围或顺序时,当轮直接新增或原位合并对应条目,不再额外询问是否写入文档.单纯探讨可能性的想法不自动登记为已确认计划;记录后续安排不等于授权立即执行.
2. 当前工作范围较大但没有明确的后续计划讨论时,Agent 认为值得持续跟踪可以先询问是否写入 PLAN;得到同意后才入档,不得仅因改动较多自行写入.普通小改不为此反复询问.
3. 修改小功能,某个代码分支,文件或脚本,以及局部排障,重构,测试和临时实施步骤,默认不改 PLAN.即使执行时拆出了步骤,发现了问题或完成了修改,也不自动新增或事后补记计划.重要发现仍在交付或已有真源说明;需要形成新的后续计划时先按上述条件确认.
4. 已登记计划只在讨论调整,必要的剩余验收条件实质变化,或满足关闭条件时更新对应条目.满足约定验收条件后,按下方更新时机在当轮收口时直接删除已完成条目,无需再次请求删除确认;仅代码已改而验收未完成时保留为待验收.用户明确取消或替换计划时删除取消项或原位更新,不把取消当作完成.

完成一项已登记计划需要清理,完成一项从未入档的小修改不需要碰 PLAN.只核对本次相关条目,不要求每轮重写状态或扫描清理整份文档;全量收敛仅在用户明确要求时进行.保留仍有效的项目目标,约束,决策和未解决风险,不为清空计划而删除长期事实.

FEATURES 独立按主要能力,重要使用方式,兼容性,限制或证据可信范围的实质变化判断是否更新;内部重构,恢复已有约定或等效重跑测试不强制更新.两份文档可以都不更新,不强制成对修改.

已登记事实被可靠证据明确推翻时,在授权范围内最小纠正或报告,不借纠正事实新增未确认计划或持续跟踪局部事项.授权整理时按当前入档条件核对已有条目,保留重要未解决项及必要证据,移除失效或不符合职责的内容;移除局部记录不代表问题已解决.

读取文档不等于必须修改.免更新不免除相关测试,review,安全检查或项目已有的修改记录要求;结果留在本次交付或既有真源,不为解释免更新而新增管理文件或逐次审计记录.

## 更新时机与本轮收口

先按更新条件判断是否需要写入,再按本节安排时机.三个文件独立判断,不因开始任务,完成代码修改,准备提交或提交成功而全部刷新;不以更新时间,提交编号或工作树状态作为刷新理由.这些规则须简明写入生成的 AGENTS,让后续开发无需重新调用本 Skill.

| 文档 | 更新时机 |
| --- | --- |
| `AGENTS.md` | 已确认的稳定开发规则,验证入口或文档路由发生变化时,在后续受影响操作开始前更新并重读;纯结果记录不写入.不把本轮临时做法提升为规则,不在提交后补写收尾规范 |
| `docs/PLAN.md` | 后续计划或调整讨论明确后当轮写入,需要指导本轮实施的决策先写再执行;已有条目取得约定验收证据后,在本轮收口时删除.不因代码写完或提交成功提前认定验收通过 |
| `docs/FEATURES.md` | 实现与相关验证结果确定后,按主要能力和可信范围的实际变化更新,在本轮收口前完成.新证据已否定旧声明时及时收窄或纠正,不能等到全部测试成功才处理;等效重跑不刷新 |

本轮收口按是否要求 Git 提交区分,不是将文档维护延迟到 Git 操作:

1. **修改但不提交**:必要的规则与计划先更新 -> 实施并执行相关验证 -> 按证据关闭已有计划,更新受影响事实 -> 回读并核对实现与文档一致 -> 交付.需要的文档变更与代码一起留在工作区,不等待下一次提交才补写,也不自动暂存或提交.仅讨论明确计划时无需实施或运行代码验证,当轮写入并回读后交付.
2. **明确要求提交**:在本批最终暂存及提交之前,完成所有满足更新条件且在授权范围内的文档修改,包括已验收 PLAN 条目的删除.次序为实施与相关验证 -> 文档收口 -> 最终差异审查及受影响检查 -> 精确暂存本批实现与对应文档 -> 提交 -> 只读核对提交结果与剩余差异 -> 报告.规则或计划若影响实施仍按上表提前处理.暂存后又修改了本批内容时,重新审查并更新对应暂存内容,不能提交旧快照.仅要求提交已有修改时也核对本批相关文档是否已收口,但不启动新开发或全量文档整理.
3. **提交后边界**:同一轮提交收尾只核对和报告,不再补写上述文档,不为记录提交成功,提交哈希或工作树干净而制造新修改.发现遗漏或提交后才取得的新证据时,如实报告待修正内容;除非用户已授权后续修正,不自动补写,追加提交或 amend.用户随后明确的新任务按新一轮处理,不受上一轮收口限制.
4. **验收或范围未满足**:失败或未运行的验证不能关闭对应计划或新增成功能力;可在范围内纠正已被证据推翻的声明.验收依赖提交后 CI,部署或外部确认时,提交前保留未验收项,不能提前删除;结果按上一条处理.用户限制只提交指定文件或只处理已有暂存内容时遵守限制,不夹带文档修改,在报告中说明必要但未纳入的文档及原因.保留用户原有和无关改动,不以整个工作树干净作为本批完成条件.

本节规定后续开发的顺序,不授权本 Skill 查询或操作 Git.本 Skill 仍只执行已授权的建档或校准,不为实现收口规则主动运行 Git.项目已有的其他必需文档也应在提交前按其职责收口,避免将同一问题转移到 EXPERIENCE 或修改记录.

## 文档增长控制与退出条件

每次准备新增内容时,先判断它是否改变后续开发行动,当前决策或能力可信范围,再找同主题的已有真源.没有新的长期信息就不写;有变化则原位合并,只保留必要结论与证据入口,不追加日期块,重复测试过程或完成报告.可直接从配置,源码或自动化检查可靠取得的细节使用指针,不人工维护副本.

日常维护只核对本次触及的主题;用户明确要求整体收敛时才检查全部授权文档.以下规则既用于本次授权写入,也须压缩为生成文档中的日常维护要求,避免基线建立后重新变成只增不减的日志.

| 对象 | 保留与更新 | 退出条件 |
| --- | --- | --- |
| AGENTS 开发入口 | 全项目必须遵守的行动约束,稳定命令与按任务读取入口;专项细节由原规范拥有 | 重复规则合并,明确失效的规则移除;机器检查已完整表达的细节改为入口,但不因此移除授权,隐私或检查无法覆盖的边界.单次事故与执行结果不进入根规则 |
| PLAN 工作项与纠偏 | 经讨论确认或同意入档的未完成计划,相关依赖,验收条件和阻塞 | 满足约定验收条件后按更新时机在当轮收口时直接删除对应条目,不等待另一次整理或删除确认;长期结论按需归回原真源,不保留完成列表或流水账 |
| PLAN 目标与决策 | 仍有效的选择,必要理由及边界;专项细节只留指针 | 仅在明确被替代或不再适用时移除旧方案;未确认提案不能替代现行目标,久未处理不等于取消 |
| FEATURES 能力 | 每项主要能力一处,附实现位置,必要的成功验证依据与限制 | 能力确已移除时删除该声明;验证失效或新证据否定时收窄声明,后续缺口按更新条件归属,不能继续冒充成功 |
| FEATURES 验证证据 | 仅在能力结论或可信范围变化时更新必要摘要或持久证据指针;等效重跑不要求刷新 | 被等效覆盖的逐轮过程可以删除;旧证据仍提供独有且有效的平台或行为覆盖时保留最小摘要,不能只凭测试数量较多或日期较新替代 |
| EXPERIENCE 项目经验 | 按问题机制或适用条件合并结论,直接证据和例外;相同经验只保留一处 | 重复案例并入原条目,明确不再适用的经验移除;已由规范或回归测试完整承载时保留必要指针与剩余例外,不重复教学过程.未经核实不能仅因年代久远删除 |
| 当前专项规范与测试定义 | 每个主题保留当前有效规则,前提和验收;指向详细决策或执行记录 | 明确替代的旧操作和重复定义退出当前正文;执行结果不逐轮追加到用例定义,过往失败不能被改写成成功 |
| ADR,已关闭 Bug,发布或测试历史 | 按项目现有约定保存决策或证据,关闭后不追加无关工作;更正使用明确勘误或替代关系 | 从当前工作入口移除已关闭状态,保留仍相关的稳定链接.历史记录的删除和归档只按已有保留约定或明确授权,不因入口变短而删除唯一证据 |

### 篇幅复核与拆分

- 新生成的根 AGENTS 以约 60 行简短规则为阅读参考;超过 100 行或出现多段案例,长表和过程叙述时,交付前复核每条是否必须常驻.这是复核信号,不是删除配额;不得通过合成长行伪装简短.已有文件超出参考不自动授权整体重写.
- 其他文档不设通用硬上限.出现同主题重复,已关闭项持续堆积,现状和历史混杂,或完成普通任务必须读取大量无关正文时,先合并和移除授权范围内的冗余.内容确有必要时保留,在交付中指出超出本次范围的结构问题,不每轮增加提醒条目.
- 合并和删减后仍混有不同读者,维护责任或生命周期,且已有文档无法承接时才考虑拆分;须已获准新增或移动相应文档.每个新文件必须有独立职责及有效入口,不能按日期,固定行数或每次任务自动分卷.根入口指向主题入口,不枚举全部历史案例;拆分后删除被替代的重复正文,核对旧引用和唯一证据仍可定位.

收敛前完整读取授权目标,核对相关当前实现,已确认选择与验证范围.对拟移除的信息判断为不符合本文件入档条件,重复,已验收关闭,有证据失效,或已由可解析的权威指针承载;无法判断则保留并报告.不把删除文档中的过时描述误当获准删除实际能力,不为变短而隐去影响当前决策或能力可信范围的失败,跳过项或风险.

完成日志和一次性调查过程留在交付报告;需要长期保存的实质变更使用项目已有的修改记录或已确认历史来源,不自动新建归档,台账或追踪框架.大幅收敛前确认当前文档内容有可恢复副本,不将本机备份路径写入项目事实或作为证据依赖.

回读时反向核对:符合入档条件的未解决项和待确认选择仍在,未入档局部问题已在交付或已有任务真源交代,有效约束和决策理由未丢失,当前能力没有被扩大,独有证据与失败边界仍可定位,旧方案不再与现行方案竞争.来源归属不清,证据不足或出现并发修改冲突时停止相关删减并报告,不得猜测恢复或覆盖.篇幅变化仅是结果,不替代上述质量验收.

## 证据优先级与陈旧状态

- 目标,非目标和约束来自用户明确要求及项目中有效的高层规则.用户已明确覆盖的旧约束按其授权范围处理,不重复确认;仍无法按指令优先级和明确授权消解的实质冲突才停止并请求确认,不得静默改写事实.
- 当前实现状态以当前工作区中的源码,配置和可观察行为为准.README,旧计划,历史测试结果和注释用于发现线索,不能推翻更新且可验证的当前证据.
- 成功执行的相关本地验证证明本次观察到的行为.既有验证记录只有在可核对被测内容与当前实现一致,验证命令和适用范围明确时才可使用;它不能覆盖验证后发生的变化.失败,未运行或无法绑定当前状态的验证只能形成风险,缺口或开放问题.
- 现有目标文档的描述被当前证据明确推翻时,在原职责内最小纠正.如果只是疑似陈旧或涉及设计理由,保持不写并报告冲突.
- 多处描述不一致时,先确定各自职责;对当前状态采用最新且可验证的证据.不得修改本次未授权的文档来制造一致;显式校准可以包含用户指定的项目文档,但不扩大到源码或配置.

便宜且可重复获取的计数,版本或状态优先指向产生它的配置或命令,不要把瞬时数值写成长期事实.数值确实作为验证证据或昂贵测量结果保留时,同时记录观察日期,精确命令或测量对象,适用范围以及影响复现的环境条件.

## 可移植性与敏感信息门禁

- 不写入 API key,token,密码,连接字符串,带凭据的 URL 或其真实片段.秘密的存在与项目工作相关时,只记录稳定名称或团队共享保管位置.
- 不写入与个人本机,私有基础设施或凭据绑定的用户名,用户主目录,仓库外本机绝对路径,主机名,IP/MAC 地址或本地环境变量值.项目自身的操作系统约束以及公开,非敏感且确有必要的端点信息可以保留在其权威位置.
- 文件引用使用仓库相对路径;外部引用必须能由项目协作者共同访问.不得让基线依赖当前 Agent 的私有记忆,会话记录或本地临时文件.
- 写入前扫描待新增内容,发现敏感值时完全排除,不要用部分遮盖的真实值充当脱敏.如果已有目标文档疑似包含敏感值,在任何写入前停止,不要回显该值;只报告文件和风险类别,由用户决定清理与凭据轮换.

## `AGENTS.md`

目标是让下一位开发者快速知道可以改什么,不能破坏什么,如何验证及何时更新文档.用少量主题标题和短条目组织,每条说明具体对象与要求;避免口号,长段复盘,日期流水和重复禁令.按实际内容选用项目范围,开发边界,验证,文档与交付等主题,不为凑模板建立空章节.

生成时将工程开发工作流转化为当前项目的短入口与任务路由,保留实际文档路径和必要验收要求.不要整篇复制工作流说明,也不要仅列链接而省略读取条件.后续 Agent 应能沿入口完成任务,不需要重新调用本 Skill 才能日常开发.

### 项目开发规则

- 从用户明确要求,现有有效规则和已确认的项目设计提炼产品范围,支持平台,模块职责,依赖方向,关键行为不变量及外部系统边界.只有源码事实时可说明当前结构,不得把偶然实现提升为永久约束;空项目不虚构技术栈,硬件或架构.
- 开发要求保留最小必要修改,复用现有能力与成熟依赖,不顺手重构;重要设计优先核对已有规范与成熟参考.日志,隐私,资源释放,异常恢复等规则按项目实际风险和已确认要求选择,写成可检查的行为.
- 使用已有且可确认的稳定验证入口;没有入口时如实说明,不猜命令.按变更影响验证正常与必要的边界/失败路径,区分实际通过,实际失败和未验证;编译或单元测试不能代替尚未执行的目标环境验收.
- 详细操作和依据已有权威文档时,只保留关键规则与相对链接.参考文档只提供写法和规则组织思路,不得复制其项目名称,技术栈,设备约束,历史事故或自动提交策略;引用目标必须在当前项目存在.

### 文档维护规则

在生成文件中简明覆盖以下语义,不逐段复制本 Skill 的完整流程:

- 开始工作读 `docs/PLAN.md`,判断能力读 `docs/FEATURES.md`,复用经验读 `docs/EXPERIENCE.md`.
- 讨论明确的后续计划直接更新其任务真源,PLAN 保存自有计划或必要指针;未讨论但较大的工作须同意后入档,普通局部修改不登记或事后补记.入档不授权立即实施.PLAN 自有计划验收通过后当轮直接删除,无需另问;未验收保留,取消或替换时同步调整,不留完成列表.外部任务与证据仍按其原契约维护.
- FEATURES 仅在主要能力或可信范围变化时更新,新增能力需实现与成功验证依据;EXPERIENCE 只收已证实经验.PLAN/FEATURES 独立判断,免更新不免测试,review 和既有修改记录要求.失实事实在授权内纠正,不据此新增未确认计划.
- 更新时机:稳定规则及需指导实施的已确认计划在受影响操作前更新并重读;能力事实在实现与相关验证结果确定后更新.本轮不提交时,必要更新与 PLAN 验收关闭在交付前完成;要求提交时,全部前移到本批最终暂存及提交前,随对应实现纳入授权提交范围,暂存后再改须重审并更新暂存.提交后只读核对并报告,不补写文档或自动追加/amend;遗漏及提交后才取得的证据留在报告,后续修正须有用户授权.依赖 CI/部署等未完成验收的计划保留,不得预先关闭;限制文件或仅提交已有暂存时不扩范围,说明未纳入项,保留原有和无关改动.
- 写入前先找同主题真源,没有新的长期信息不写;经验合并为机制,证据与适用边界,不按事故逐条累积.本次触及的重复或明确失效内容及时收敛,有效决策,未解决风险与独有证据保留.当前规范与历史结果分开,根入口不收复盘和逐轮测试;超出职责先合并,仅在独立职责且已授权时拆分,不自动归档或按篇幅裁剪.交付前核对受影响文档与指针.
- 当前纠偏及专项指针归 PLAN,AGENTS 只存稳定规则.只有用户已确认且仍有效的纠偏可在明确范围替代指定旧决策,不能覆盖更高规则或无关约束;不明冲突先报告.验收关闭后解除替代关系,长期事实归回原真源,恢复相关工作前重读更新内容.

### 交付与压缩检查

- 明确写入:文档生成或更新完成后不自动暂存,提交或推送,版本管理操作须用户另行明确要求.参考文件中的“完成即提交”不得覆盖此要求.本次建档不修改代码的限制仅约束本 Skill 执行,不得变成项目长期禁止修改代码的规则.
- 按上方篇幅复核规则检查正文:适用开发约束,验证入口和文档路由应完整且每条能指导行动.删除重复表达与过程叙述,保留独有约束和可解析指针;生成文档须独立可用,不能要求后续开发者读取本 Skill 才知道维护规则.
- 已有非空 `AGENTS.md` 时保留全部有效规则,只补充缺失且兼容的职责.简短要求不授权整篇重写旧文件;用户明确要求收敛时才按校准范围压缩.临时调查,未经确认的命令和历史结果不进入根契约.

## `docs/PLAN.md`

用中性项目语言说明项目目标,已知约束与当前阶段.按上述入档条件确认后续计划后,记录目标,必要的范围或顺序,验收条件及关键依赖;有下一可运行纵向切片时说明它或阻塞它的开放问题,已有任务真源则使用指针.不复制临时执行步骤,不按工作大小推断用户已同意入档.没有已确认的后续计划时明确这一状态,不凭空制造切片,任务或阻塞项.非目标,架构决策和依赖只在已有证据或明确选择时增加,不要为了固定模板制造空标题.

只描述项目工作,证据和系统边界,不记录执行主体,会话或工作标识,运行引擎或跨任务通信约定.将已确认事实与待确认假设分开;影响项目级判断的未知项才进入开放问题,不要伪造确定性或收集所有局部疑问.纵向切片必须保持可运行的端到端路径,工作项应能对应验收标准.

发生需要纠偏的问题时才增加当前纠偏条目,不预建空白纠偏框架.记录偏差及证据,适用范围,用户确认依据或待确认状态,拟替代的具体旧决策,行动,验收与关闭条件.只有已确认且仍活动的条目可以改变后续工作的依据;判断有偏差本身不授权目标变更或实施.

普通纠偏正文保存在 `PLAN.md`.复杂跨阶段事项才按需使用 `docs/CORRECTION.md`,由 `PLAN.md` 保存简短定位和指针,专项文件拥有完整内容与唯一状态;两处不维护重复正文或竞争状态.若已有合适的专项真源则复用其指针,不新增第二份.专项文件不成为固定第五份基线或最高优先级指令文件.

## `docs/FEATURES.md`

作为当前主要能力的总览与导航,只记录同时具备实现证据与成功验证证据的能力,不枚举所有局部功能.每项用最小必要内容说明:

- 当前可观察的主要能力及适用范围.
- 实现证据,例如源码或配置路径.
- 支撑该能力结论的验证摘要或持久证据指针,能够定位实际成功观察的对象,范围与状态.已有专项文档或可访问且绑定版本的 CI 记录承载详细日期,命令,环境和结果时,引用而不复制全过程.
- 已证实的限制或边界.

没有合适持久真源,或独有证据对理解能力边界确有必要时,在本文件保留最小观察摘要,包括日期,稳定入口或专项命令,范围,结果及相关环境/工作区或版本.不为每次测试新增证据文件,也不以临时会话链接替代必须长期保留的独有证据.普通执行流水留在交付报告,重复验证且结论未变时不刷新本文件.

计划能力,说明文档中的声明,历史成功记录,未运行的测试和推测不得冒充当前已验证功能.历史证据须核对当前适用性;失败或失效证据只能收窄能力结论或标明限制.没有合格能力证据时保留明确的空状态.

## `docs/EXPERIENCE.md`

只记录经过实际实施或验证后证实的经验.每项说明经验结论,直接证据,适用边界和已知例外.不记录一般建议,尚未验证的猜测或仅来自说明文档的主张.没有合格经验时保留明确的空状态.

## 写入与一致性验收

1. 在写入前完成所有目标路径,现有内容,语义职责和冲突检查.
2. 根据所选分支生成或补充三个 `docs` 文档,将每项信息路由到唯一权威位置.
3. 对目标文档执行反向一致性检查:新增和保留条目均符合入档条件,已完成且已验证的能力不再留作开放工作,失实描述已按职责纠正或移除,局部过程与已失效方案已收敛,重要未解决项及必要证据未丢失,文档之间没有职责重叠或事实矛盾,所有指针均可解析.
4. 按上方 AGENTS 契约核对开发规则具体且有依据,表达简短,文档路由完整,无自动提交规则,验证入口仍由当前配置支持.`FEATURES.md` 不把计划或失败验证写成成功能力,`EXPERIENCE.md` 不含未证实建议.执行敏感信息和衍生数值检查.
5. 先完成并回读三个 `docs` 文档,最后创建或补充 `AGENTS.md`,再回读四份文档.任何目标未完成时不得声称基线已经建立.
6. 本 Skill 不拥有的外部文档存在冲突时只报告,不得顺手修改.
