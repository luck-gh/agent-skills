# 建立工程化 Agent 开发基线

为软件项目建立可持续指导 Agent 开发的工程规则与事实基线:明确每类任务先读什么,按什么约束实现,如何验证,结果写回哪里.本 Skill 负责建立这套规则和文档,不在建档后继续实施功能,也不创建单次会话 handoff.

## 先区分请求

- 初始化或首次接管:用户要求建立 Agent 开发规范,或直接调用本 Skill 且未限定只读或校准时,即授权建立或补齐工程开发基线,不再询问是否建档.单纯讨论点子或只读了解代码库不触发初始化.
- 显式校准:用户明确要求判断项目偏航,依据目标与当前证据更新指定项目文档,或收敛其过时和重复条目时进入校准流程.不要求基线缺失,也不自动补建四份文档;只要求分析时不得写入.
- 两者都明确要求时先完成基线,再按已授权范围校准.不能从一次 Skill 调用推断用户批准了新的目标或纠偏实施.

## 建档授权与写入边界

- 基线可补齐时,直接在目标项目创建缺失的 `docs/PLAN.md`,`docs/FEATURES.md`,`docs/EXPERIENCE.md`,填充空文件或补充缺失职责,最后创建或最小补充 `AGENTS.md` 的项目开发规则与文档路由.已有有效内容和用户已有改动必须保留.
- 本流程只负责项目文档,不启动软件开发或交付流程.补齐基线的授权不扩展到任意文档整理或显式校准.用户本次明确要求只读或另行限制写入时按其要求执行;更高优先级指令,宿主权限,路径与敏感信息门禁仍须遵守.
- 不修改任何项目代码,测试代码,脚本,配置或依赖文件,不安装或升级依赖.
- 本 Skill 只负责项目文档,不主动查询或操作 Git,不以分支,暂存状态或远端同步作为建档前置条件.生成或更新完成后不自动暂存,提交或推送;用户另行明确要求的版本管理操作,作为独立任务处理.

## 定位项目根并检查指令入口

1. 按以下优先级确定项目根:用户明确指定的目标,当前上下文已明确的项目根,唯一的 workspace root,当前目录.只有按此顺序仍无法唯一确定目标时才询问用户.
2. 只用项目根直属的 `AGENTS.md` 与 `AGENTS.override.md` 判定根级契约,并按原始名称和原始路径类型检查.不得搜索父目录,子目录或全局位置来替代它.如果当前运行上下文已明确标出一个通过平台配置加载的根级非标准指令文件,停止并报告,不得创建会遮蔽它的 `AGENTS.md`;不要自行扫描全局配置猜测文件名.
3. 存在大小写不同的同名项,目录,符号链接,Junction,reparse point 或 broken path 时停止并报告,不得跟随或覆盖.
4. 根目录直属 `AGENTS.override.md` 会优先于待建或已有的 `AGENTS.md`,因此只要该原始路径存在就停止并报告.不得创建一个实际不会生效的根契约.

上述范围只用于判定根级契约.写入前仍须按平台优先级检查并遵守对实际目标文档生效的嵌套项目指令;例如普通的 `docs/AGENTS.override.md` 或 `docs/AGENTS.md`.合法的 override 优先级本身不是冲突.只有路径异常,无法唯一确定实际生效的指令,或有效指令与本次文档写入冲突时,才在任何写入前停止并报告.

完成入口检查后,完整读取已有普通 `AGENTS.md` 和[项目文档公共契约](references/project-document-contract.md).建立或补齐基线时,读取[Agent 工程开发工作流](references/engineering-workflow.md),先识别现有文档职责与任务读取入口,再判定基线状态.显式校准直接读取[显式校准与纠偏](references/explicit-calibration.md),跳过下方基线状态判定及两个初始化分支;仅当校准范围包含开发规范或文档分工时,同时读取工程开发工作流.公共契约的固定四文件预检与写入顺序仅用于建立或补齐基线,校准按实际授权目标预检和回读.

## 判定基线状态

仅对初始化或首次接管,按已读取的公共契约一次性检查 `AGENTS.md` 和三个目标文档,并分为唯一状态:

- 完整:基线步骤只读 no-op,不重写或重新初始化;仅要求初始化时退出,同时明确要求校准时继续校准分支.
- 可补齐:保留仍然成立的内容并继续.
- 冲突:在任何写入前停止并报告.

不得仅因普通 `AGENTS.md` 存在就判定完整.空文件不会构成有效指令;非空文件也可能只覆盖部分项目规则.可补齐时只追加缺失且兼容的根级职责.

## 按实现证据选择分支

只有状态为可补齐时,再根据项目证据恰好读取一个分支说明:

- 没有有意义的源码,构建配置,依赖清单或测试证据时,读取[空白项目基线](references/blank-project.md).
- 已有任一有意义的源码,构建配置,依赖清单或测试证据时,读取[现有代码库基线](references/existing-project.md).

编辑器配置,许可证或孤立的说明文档本身不构成已有实现证据.不要读取未选中的分支说明.

## 共同边界与完成标准

- 状态为可补齐时,按已读取的公共契约完成信息路由,写入顺序和一致性验收.
- 生成的 `AGENTS.md` 应是简短,具体的开发入口:项目硬约束,开发与排障流程,按任务读取专项文档的条件,验证和收口要求.四份基线连接已有工程文档,不复制另一套任务状态,不因参考项目文件多就批量新建专项文件.按公共契约落实文档进入,合并与退出规则及篇幅复核,将必要维护要求写入生成文档;不把当前规范,经验与历史记录混成只增不减的正文.本次建档不改代码的限制不得写成项目永久禁止开发.
- `AGENTS.md` 保存稳定纠偏规则,`PLAN.md` 保存当前纠偏或其唯一真源指针.疑似偏航不等于获准改目标;纠偏文件没有天然最高优先级,不得创建 `AGENTS.override.md` 来强制生效.
- `PLAN.md` 与 `FEATURES.md` 分别维护后续计划及项目方向与当前主要能力,不是任务或测试日志.PLAN 仅在讨论并明确后续计划,或用户同意将较大工作入档时新增或重排;普通小改默认不更新.已有计划满足约定验收后当轮自动删除条目,不保留完成列表.按[公共契约的更新时机](references/project-document-contract.md#更新时机与本轮收口)将三份文档的更新触发与收口顺序写入生成的 `AGENTS.md`:不提交时必要更新在交付前完成;要求提交时在最终暂存及提交前完成,提交后只读核对与报告,不再补改文档.日常维护不因此触发本 Skill 或扩大为全量文档整理.
- 开放性分析允许自行选择合适方法与只读工具;写入必须完成路径,授权,证据及敏感信息预检,保留有效内容并回读.失败或部分写入时停止并报告实际状态,不宣称完成.
- 按所选分支完成一致性验收.只读校准交付证据与判断;获准写入后交付已回读的文档及未解决项.不把文档计划当作实施或验证结果.
- 完成后交付并结束当前工作,不把再次确认作为建档完成的条件,不得继续编码.受纠偏影响的工作恢复前显式重读相关规则与活动条目,不假定运行中的任务会自动刷新上下文.

交付时简洁列出项目根,采用的模式,基线状态或校准结论,实际读写范围,纠正项,保留项,验证结果及待确认事项.
