# Skills 功能与使用示例

不知道该选哪个 Skill 时,先看下面的用途和示例.安装方式见 [README](../README.md),版本变化见 [CHANGELOG](CHANGELOG.md).

示例中的 `$skill-name` 表示显式调用对应 Skill;请先安装,并将 `<...>` 替换为实际信息.各条目的完整规则以链接的 `SKILL.md` 为准.示例不代表跳过文件覆盖、软件安装或外部操作所需的确认.

## bootstrap-project-context (建立工程化 Agent 开发基线)

为新项目或已有代码库建立工程化 Agent 开发基线:明确开发规则,任务与规范的文档分工,按需读取,验证和事实更新流程;也可按明确请求校准项目方向与指定文档.四份基线连接已有任务,架构,日志,测试,Bug 和交付真源,不复制状态或批量建立空模板.初始化仍区分完整,可补齐和冲突;只读判断不写入,不用于普通功能开发或一次性会话总结.

生成的 AGENTS.md 用短条目表达项目范围,开发边界,验证要求与文档路由,按目标项目证据提炼,不照搬参考项目事实;文档生成后不自动暂存,提交或推送.纠偏默认记录在 PLAN.md,AGENTS.md 只保留稳定规则;复杂跨阶段事项才使用专项文档及指针.只有已确认且仍活动的纠偏能在明确范围内替代具体旧决策,不存在自动获得最高优先级的文件.

也可明确要求收敛指定工程文档:同主题原位合并,已验收计划退出,经验按机制归并,当前规范与历史证据分开.新 AGENTS 以约 60 行短规则为参考,超过 100 行复核常驻必要性,不机械截断.其他文档按重复,失效和职责混杂收敛,保留未解决项与独有证据;先合并再按独立职责及授权考虑拆分,不自动建立归档,不用于一般排版润色.

[使用说明](../bootstrap-project-context/README.md) | [Agent 执行规则](../bootstrap-project-context/SKILL.md)

使用示例:

```text
使用 $bootstrap-project-context,为当前软件项目建立可持续交接的文档基线.先核对现有实现和文档,保留已有规范,补齐 AGENTS.md 以及 docs 下的 PLAN.md、FEATURES.md、EXPERIENCE.md.只记录有证据的当前能力,本次不实现新功能.
```

```text
使用 $bootstrap-project-context,对照 docs/PLAN.md 中已确认的目标,检查当前项目方向是否偏离.本次只读,区分有证据的偏差和待确认事项,给出最小纠偏建议,不要改写目标或实现代码.
```

[使用说明](../capture-personal-knowledge/README.md) | [Agent 执行规则](../capture-personal-knowledge/SKILL.md)

```text
使用 $capture-personal-knowledge,复盘下面这段排障记录,判断哪些内容值得复用,适合放笔记、记忆还是不保存.先给出候选内容和建议去向,去掉账号、客户信息和本机路径,本次先不要写入.

```

## diagram-codebase (架构速览与详解)

分析代码或文档中的架构与关系,默认交付可编辑的 draw.io 速览图和可独立阅读的 Markdown 详解.适用于 Python、嵌入式 C、HDL、Skill 路由和笔记关联.无论工程大小,都先由离线工具扫描文件,再由 Agent 根据结构摘要选择问题、查询必要的局部源码并生成图文,不是把整个工程交给模型逐文件阅读.

[使用说明](../diagram-codebase/README.md) | [Agent 执行规则](../diagram-codebase/SKILL.md)

### 什么时候需要工程环境?

模式取决于要回答的问题,不是工程大小,也不是“只要是 C 就必须准备环境”:

| 你要了解什么 | 选择什么模式 | 如何处理工程环境 |
| --- | --- | --- |
| 整体架构、模块职责、接口和源码中的调用线索 | 默认源码结构模式 `source` | 不主动查找 SDK、编译器或构建参数,不创建环境配置 |
| 源码中有哪些条件分支,暂不确定当前启用哪侧 | 源码结构模式 `source` | 保留可提取的分支与未求值条件,不把互斥路径说成同时运行 |
| Python 静态关系、Skill 条件路由、Markdown/Obsidian 文档关联 | 通常使用源码结构模式 `source` | 不准备目标项目的运行环境,不执行模块导入或文档中的命令 |
| 某个板型、产品版本或构建配置实际选用了哪些 C 实现 | 配置感知模式 `configured` | 先复用已有有效配置,不足时定向提取;关键宏或目标不明确时询问用户 |
| 需要结合宏展开、头文件定义或目标参数核对 C 关系 | 配置感知模式 `configured` | 按问题补齐必要输入,不是无条件收集整套环境;静态解析仍不证明实际运行效果 |

“不关注工程环境”不等于“不需要离线工具”.工程环境指被分析项目的 SDK、头文件路径、宏和目标参数;工具环境指本 Skill 自己使用的 Python 和解析依赖.两种模式都先复用已有工具环境,缺依赖时报告并取得安装授权,不自动安装或升级.

两种模式也不是“换个提示词让模型分析同样的数据”.例如源码有 `#if BOARD_A` 和 `#else`:源码模式保留两侧及条件,不判断当前选择;配置感知模式按已提供的宏分析选中部分.源码中的 `foo()` 只提供调用表达式线索,仍可能是宏或函数指针;Agent 不能凭名称猜成已确认的跨模块调用.扫描失败时不会偷偷切换模式并宣称等价完成.

已有 `analysis-config.json` 在源码模式下原位保留,不自动读取、重建或删除.配置感知模式需要时才消费它并检查来源变化;正常复用不重复构建.显式传入配置的脚本调用必须选择 `--mode configured`,源码模式不会静默忽略配置参数.

配置参数直接传给工具,不先落盘一份草稿;只保留正式 `analysis-config.json`,更新失败保留旧文件.图文的候选检查流程保持不变.

### 怎么写提示词

以下内容发给 Agent,不是在终端执行的命令.已接入 Skill 后,普通分析只需这一句;Agent 按 Skill 约定默认选择源码结构模式:

```text
请使用 $diagram-codebase,分析当前工程,按默认约定生成架构图和详细说明.
```

明确要分析一个构建版本时再补充目标,例如:

```text
请使用 $diagram-codebase,以配置感知模式分析当前工程的 Release 构建,生成架构图和详细说明.优先复用已有有效配置;关键配置不明确时先问我.
```

将 `Release` 换成实际的构建名称或板型.未接入 Skill 发现入口时,把提示词中的整个 `$diagram-codebase` 换成其实体目录绝对路径即可;“当前工程”不明确时补上目标工程路径.不需要每次复述绘图重点、证据格式、默认目录或离线先行规则.

### 输出与当前边界

默认在目标工程的 `docs/architecture/` 生成 `overview.drawio` 速览图和 `overview.md` 详细说明,后者可独立呈现完整结构、模块接口、必要流程及逐项证据.需要新建可复用配置时,同目录按需增加 `analysis-config.json`;候选和备份等过程文件放在 `_work/overview/` 下.用户指定的目录和名称优先.工具下载、venv 和扫描缓存仍在 Skill 实体目录的 `tools/local/`,不散放到目标工程或用户目录.

第一版新增的无工程环境解析覆盖 C 和 `.h`;Python、Markdown 复用现有静态解析.数字 Verilog/SystemVerilog 仍有预处理及实例展开限制,Verilog-A 尚未接入,不能因为提供两种模式就宣称所有语言都支持配置感知分析.语法错误和未解析关系仍需报告;源码模式成功不代表编译通过,结构检查也不代替图文视觉复核.详细契约见 [模式与离线流程](../diagram-codebase/references/offline-analysis.md) 和 [按需初始化](../diagram-codebase/references/initialization.md).

## distill-person-thinking (人物思维蒸馏与调用)

从公开、可追溯的材料中整理人物思维模型,也可以查找已有公开 Skill,或使用已有模型分析任务.显式调用并要求推荐时,根据当前对话按领域、任务、方法标签匹配 1-3 个具体模型.显式要求思维风暴时,自主选择互补视角,独立分析、交叉质疑,比较并选择方案.随包模型覆盖投资、商业、工程、产品、研究、教育与传播;普通用户蒸馏成果独立存放,不进入 Skill 分发目录.

[使用说明](../distill-person-thinking/README.md) | [Agent 执行规则](../distill-person-thinking/SKILL.md)

[人物与领域索引](../distill-person-thinking/references/model-index.md)提供两种浏览方式:按常用名/别名查人物,或按科技与产品,芯片与半导体,AI,金融投资等方向查具体方法.内置文件优先采用通行中文姓名或网名,例如 `思维模型_乔布斯.md`,`思维模型_野兽先生.md`;姓名中点在文件名中统一写为下划线,例如 `思维模型_伊利亚_苏茨克维.md`,正文姓名仍保留正常写法.稳定人物标识 person_id 与文件名分开.跨领域链接始终指向同一文件,不会重复加载;中文名和英文别名都可以用于调用,例如野兽先生与 MrBeast 指向同一人物.原有外部人物库无需改名.

使用示例:

```text
使用 $distill-person-thinking,根据我提供的公开文章与出处,蒸馏理查德·费曼在解释复杂问题时采用的思维方法.人物资料库使用 <已有资料库的绝对路径>.区分原始证据和推断,不要模仿本人发言,不要覆盖已有不同人物的模型.
<在此提供公开文章及可追溯出处>
```

```text
使用 $distill-person-thinking,根据我们刚才讨论的问题推荐最多 3 个当前可用的思维模型,说明具体模型、匹配理由和局限,先不要应用.
```

如需直接执行,可改为:「推荐最适合的一个模型,并用它分析当前方案」.每个人物一个完整核心文件,其中可包含多个思维方法,标签、步骤、局限和必要出处导航都在同一文件.新建人物时,实际采用的外部材料按[来源蒸馏规范](../distill-person-thinking/references/source-distillation.md)整理成有方法、案例和证据边界的本地笔记,内置放在 `models/sources/`,外部放在对应资料库的 `sources/`;核心链接笔记,笔记保留原始网页.不会直接复制网页或把推断写成本人观点,关键判断仍回写核心.现有 34 位内置人物的 94 条方法出处均已整理为本地笔记,覆盖 61 个具体模型;每篇标明实际阅读范围,不代表通读人物全部著作.普通使用和推荐只需核心,深入案例或证据分歧才读取相关笔记;普通调用不为外部旧库批量补文件.内置模型无需配置外部资料库;社区候选必须先核验蒸馏,不能冒充已可用模型.

```text
使用 $distill-person-thinking,针对我们刚才讨论的行业机会开展思维风暴.请自行选择互补的思维模型,围绕同一问题独立分析并交叉质疑,给出方案对比,最后推荐一个方向和最小验证步骤.
```

默认选 3-5 个人物视角,已有明确约束时直接执行.如果希望自己选,在提示中加「先给出对比,最终方案由我选择」;也可明确指定人物.具备子代理能力时可并行,否则会说明采用单 Agent 多视角推演.只说普通「头脑风暴」或讨论如何维护此 Skill,不会触发这个模式.人物来源链接保留备查,使用时不逐一联网打开;当前行业事实需要时另行核验.

科技、芯片和 AI 场景示例:

```text
使用 $distill-person-thinking,对当前产品下一阶段该做功能扩展还是性能优化进行思维风暴.沿用对话中的用户反馈、预算和交付期限,自主选择产品、工程和验证视角,给出首选及改变选择的条件.
```

```text
使用 $distill-person-thinking,针对我们讨论的 AI 芯片项目开展思维风暴.按真实瓶颈选择架构性能、制造成本、软件生态、客户需求与失败风险方面的互补模型,不要求每个领域都安排一人.比较自研硬件、利用现成硬件优化软件、先验证需求三条路线,排除不符合预算和周期的方案,推荐最小验证步骤.
```

```text
使用 $distill-person-thinking,对当前 AI 研究路线开展思维风暴.按我们的任务和实验资源,比较扩大训练、改进数据、引入世界模型或强化学习等适用方向;选择有证据且互补的研究视角,明确能区分假设的实验.先给具体选项和你的倾向,最终方案由我选择.
```

## orchestrate-subagents (纯总控多代理编排)

显式调用后,当前主任务担任纯总控,按独立成果拆分工作,自动为内部子代理选择当前工具支持的模型,推理强度和领域 Skill,再统一协调和验收.默认在质量达标后节省资源,复杂执行也可以使用强模型;不会为了模型分级增加代理层.普通请求或仅讨论该 Skill 用法不会触发编排.

主任务沿用你在应用中选择的模型,Skill 不会自动升级主任务自身.内部子代理需要覆盖模型时,按工具约束使用独立或有限上下文并传递完整任务包.明确要求继承模型或指定有效模型时遵从你的要求;不可用或参数冲突会说明,不会静默换成其他指定值.领域 Skill 提供流程与规范,不能补齐宿主缺少的工具或权限.

默认在当前任务内收口.只有你明确要求才创建侧栏独立任务,其模型参数遵守对应工具的限制;仅调用 Skill 不等于授权给侧栏任务覆盖模型,也不授权其他外部操作.

[使用说明](../orchestrate-subagents/README.md) | [Agent 执行规则](../orchestrate-subagents/SKILL.md)

使用示例:

```text
使用 $orchestrate-subagents,根据已提供日志整理错误码分布,并独立审查支付状态机在重复回调下的幂等性.两项都只读,由当前任务汇总结论.
```

无需额外要求“自动选模”.派发时会简短说明工作单元,模型,推理强度,领域 Skill 和选择理由.如果希望全部沿用主任务设置,可补充“所有子代理继承当前模型与推理强度”.

```text
使用 $orchestrate-subagents,在当前任务内安排两个内部子代理:一个审查 API 的错误处理,一个审查单元测试的边界覆盖.两者都只读,不要改代码或创建独立任务.由你汇总去重后的问题、证据和优先级.
```

## windows-software-install (Windows 软件安装与维护)

规划并执行 Windows 大型第三方软件的下载、安装、升级和修复,核验官方来源、安装位置、授权与回滚条件,并验证结果.适用于可独立选择目录的应用、IDE 或 SDK,不用于项目依赖安装或 Windows Update.

[使用说明](../windows-software-install/README.md) | [Agent 执行规则](../windows-software-install/SKILL.md)

使用示例:

```text
使用 $windows-software-install,为 <软件名称> 制定 Windows 安装方案,希望主要程序放在 D:\Apps\<软件目录>.先检查已有安装,核对官方来源、下载体积和目录是否可控,说明仍可能留在系统盘的组件.本次先给方案,下载和安装等我确认后再执行.
```
