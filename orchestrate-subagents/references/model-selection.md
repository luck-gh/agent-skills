# 有授权的模型选择

只在用户要求推荐或分配模型,宿主允许且当前工具支持覆盖时读取.默认继承或用户已指定有效模型时不需要本文件.模型与 reasoning 建议不改变承载,任务数量或角色权限.

## 选择边界

1. 用户明确指定且当前工具支持的值优先,即使它不在映射中也应遵从.
2. 当前工具 schema 决定可用模型和 reasoning;映射数据不得声明运行时可用性.
3. 需要推荐时,根据下面的任务画像与判断强度选择最低足够的建议等级,再读取主文件声明的模型映射 JSON 得到候选.
4. 只保留当前工具支持且画像匹配的候选;多个候选无可靠差异时写 `omitted`,不猜测.用户值无效或被拒绝时写 `refused`,不更换承载规避.

等级是本地任务分配建议,不是产品排名,价格顺序或所有任务的硬性质量上限.用户显式选择与当前宿主规则始终优先;不得修改模型目录,隐藏开关或添加兼容补丁.

## 通用等级

- `L4`:战略总控.适合根级目标解释,跨分支决策,架构与协议边界,授权边界,重大歧义,高风险升级和最终验收.对应根主控或获授权的用户侧独立根任务;选择能力更强的模型不把普通叶子提升为总控.
- `L3`:协作分支.适合确需协调后代,递归委派,整合依赖结果,复杂审查或较强中间判断的任务.递归仍以任务包明确授权为前提,复杂审查不必附加后代.
- `L2`:聚焦代码.适合边界明确但需要理解与编辑验证循环的终端任务,包括只读代码探索,目标修复,小型重构,聚焦测试和细粒度界面迭代.
- `L1`:边界吞吐.适合明确,独立,可重复且可客观验证的终端任务,包括资料或日志扫描,文档研究,代码映射,固定规则检查和重复验证.

等级不是固定流水线.`L3` 不是总控与叶子之间的必经层;`L1` 与 `L2` 均默认终端,不递归委派.

## 任务画像

选择一个主要画像,仅在消除实际歧义时补充次要画像:

- `strategic-control`:根级目标,授权,风险与最终收口.
- `cross-branch-decision`:跨分支冲突,依赖与架构决策.
- `branch-coordination`:协调后代,维护分支依赖并整合结果.
- `dependency-integration`:整合多个独立来源或执行结果.
- `complex-review`:需要较强判断的代码,协议,安全或质量审查.
- `browser-debugging`:需要观察,定位与验证闭环的浏览器问题.
- `read-only-code-exploration`:固定问题下的只读源码探索.
- `targeted-code-change`:原因或目标已清楚的小范围修改与测试.
- `focused-refactor-test`:边界明确的小型重构和聚焦验证.
- `granular-ui-iteration`:既有应用中的快速,细粒度界面修改.
- `bounded-scan`:固定范围的资料,日志或结构化结果扫描.
- `documentation-research`:边界明确的文档检索与归纳.
- `code-mapping`:只读梳理代码位置,关系与所有权.
- `repeatable-validation`:固定命令或规则下的重复验证.
- `high-volume-clear-work`:输入输出明确的高吞吐独立工作.

## 解析与 reasoning

具体模型名称只属于 JSON 数据,不得复制到 Markdown,metadata 或任务模板.根据协调深度,判断强度与编辑闭环筛选等级和画像,再与当前工具实际支持项取交集.映射不是允许列表,不阻止用户选择未映射但受支持的模型.

reasoning profile 使用 `light`,`balanced`,`deep`,`exceptional` 四个通用值:`light` 对应机械且低风险的重复工作,`balanced` 对应常规理解与编辑验证,`deep` 对应复杂逻辑,边界检查或高风险审查,`exceptional` 仅在工具支持且任务确有需要时使用.选择满足质量要求的支持值,不默认使用最高或最低 effort.
