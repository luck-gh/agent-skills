# 用户侧新任务场景

只在 `routing.md` 已确认用户明确授权创建新任务,新线程,新聊天或侧栏任务时使用本文件.

## 授权边界

- 严格遵守用户指定的任务数量,标题,目标,项目,目录,工作树,模型和 reasoning.不得额外创建审查,辅助,收集或管理任务.
- 创建用户侧新任务不等于授权它继续委派.新任务不得创建其他新任务或内部子代理,除非其任务包逐项明确授权.
- 创建用户侧新任务也不等于授权监控,取消,回调,置顶,归档,重命名,删除,发布或任何 Git 副作用.Git 副作用按主文件硬边界逐项取得明确授权.
- 用户未授权持续监控时,完成宿主要求的初始状态等待并交接后停止读取进度.不得推断未观察到的开始或完成状态.
- 模型与 reasoning 服从当前用户侧工具的专属条件.若要求用户明确指定具体模型才能覆盖,用户只说“自动选择”或调用本 Skill 均不满足该条件,应省略模型参数并说明;不能套用内部子代理的自动选模权限,也不能通过创建后发消息绕过限制.

## 创建前检查

对每个拟创建任务确认:

- 它对应可独立跟进的成果,不是当前任务中的临时步骤.
- 公用任务包足以让它脱离父任务隐藏上下文独立完成闭环.
- 前置依赖,文件/状态所有权和副作用边界明确.共享工作区存在所有权冲突时先串行化.
- 当前工具明确支持用户指定的项目,目录,工作树,模型与 reasoning 参数.不支持的参数写 `omitted` 或 `refused`,不得静默替换.
- 先按当前宿主要求查询已保存项目及仓库属性,遵从其明确规定的默认环境;用户明确要求直接使用已保存项目时使用该目录.超出用户要求和宿主默认规则的额外工作树,分支,目录或持久对象需要先确认,不得自行创建.

## 工作目录与串行 checkpoint

把执行权限和状态承载分开判断:

- `sandbox` 只限定任务可访问或可写的路径和命令,不决定任务的 workspace/working directory,也不保证多个任务看到同一份代码或 Git 状态.共享状态由创建任务时选择的项目和执行环境决定.
- 当用户要求用户侧独立 Codex 任务严格串行,且后续 checkpoint 必须继承前序任务的代码或 Git 状态时,所有 checkpoint 使用同一个已保存项目 ID,并为 `create_thread` 明确选择 `environment: { type: "local" }`,直接复用该项目目录.不得省略环境参数或隐式创建独立 `worktree`.
- 在这种共享状态的串行工作流中,`worktree` 不是绝对禁用.只有用户明确要求隔离,且交接/合并方案,目录与分支所有权以及方案涉及的副作用授权都已明确时才可选择.任一条件缺失时先询问一个最小必要问题,不得把隔离当作默认值.其他不要求继承同一可变状态的场景不受本条限制.
- 写入同一 `local` 项目目录的 checkpoint 必须保持单写者并严格串行.前序任务处于运行,等待用户,重试或状态不明时,不得创建或启动后序写任务.
- 每个 checkpoint 的任务包都要求执行方在结束写入后回传实际 working directory,本轮改动路径,以及当前 branch,HEAD 和 `git status --short --branch` 的结构化摘要;目录不是 Git 工作树时明确报告该事实.根主控确认任务已经完成,目录一致,没有在途写者,且 Git 状态符合下一 checkpoint 的前置条件后,才派发下一任务.状态缺失,过期或出现非预期改动时停止派发并进入决策.

## 创建与交接

- 使用系统提供的用户侧任务或线程工具.不得改用内部子代理工具.
- 创建请求使用主文件路由的任务契约,不要复制完整父任务历史,其他任务的结论或未经证实的预期答案.
- 成功创建后返回当前产品要求的可识别入口,并报告标题,目标,承载方式和用户后续跟进方式.
- 创建是异步请求.宿主要求初始进度时,对已返回的有效任务 ID 做一次有界等待,多个任务合并到工具允许的一次调用中;传递已有 host 与 cursor,不把 pending 的客户端标识冒充任务 ID.仅有客户端标识时,先用宿主支持的紧凑状态查询尝试取得准确任务 ID;仍无可等待 ID 或查询失败时如实交接该状态,不重建任务.此步骤不授权持续监控.
- “已创建”只表示入口存在,不得写成“已完成”.“已完成”必须有任务返回的完成结论和验证结果.

## 三种生命周期

### 仅创建并交接

用户未要求根主控代管时使用:

```text
CREATE -> INITIAL_STATUS_IF_REQUIRED -> HANDOFF -> FINAL
```

创建入口,完成宿主要求的一次初始状态等待,报告已观察状态与交接信息,然后 `FINAL`.不继续监控,不推断完成,也不期待自动回传.

### 创建并由根主控协调

只有用户明确要求统一协调或汇总时使用:

```text
CREATE -> WAITING -> ALL_REQUIRED_RETURNED -> COLLECT_ONCE -> FINAL
WAITING -> NEEDS_USER -> WAITING
WAITING -> RETRY -> WAITING
WAITING -> BLOCKED
WAITING -> CANCELLED
WAITING -> UNKNOWN
```

1. 创建后进入 `WAITING`,使用紧凑事件快照维护完成集合.只处理状态转换,完成或需要决策的更新.共享目录的串行 checkpoint 每次只创建一个,并在派发后序任务前通过上节状态门禁.
2. 缺少任务内必要信息时只补充最小信息.审批,范围冲突或用户选择进入 `NEEDS_USER`.
3. 瞬时失败只由同一任务按预算最多重试一次.验证失败返回原实施任务修复.
4. 有效快照仍显示运行时继续有界等待,正常 timeout 不是失败.状态无法确认时检查同一任务,按主文件区分 `BLOCKED` 与 `UNKNOWN`;不得创建替代任务复制可能已写入的工作.
5. 取消只在用户或任务包已授权且工具支持时执行,并记录可能的部分结果.
6. 全部必需结果齐备后只进入一次 `COLLECT_ONCE`,再 `FINAL`.

### 主任务结束后回调

只在用户明确要求当前主任务先 `FINAL`,待用户侧新任务完成后再通知时使用.创建前按主文件入口读取 `new-task-callbacks.md`,完成其能力检查,标识,单次回调和收集者规则.回调不是默认节省 token 模式.

## 任务包补充字段

在公用任务包中明确:

- 这是用户侧独立新任务,不是当前主任务内的内部子代理.
- 用户指定的标题,数量,目录,工作树,模型与 reasoning,以及每个不支持参数的 `omitted` 或 `refused` 状态.
- 共享状态的串行 checkpoint 写明同一已保存项目 ID,`local` 环境,前序 checkpoint 及其最新 Git 状态;隔离例外写明用户要求和交接/合并方案及授权.
- 用户跟进方式是直接跟进,当前根主控事件等待,或完成后回调.
- 当前任务是否获授权继续委派;默认“否”.
- 使用回调时填写主任务 ID,`batch_id`,`task_id`,总任务数和收集者;否则写“不使用回调”.

## 验收与汇报

- “进行中”表示工具已证明任务开始但尚未满足验收标准.
- “已完成”要求结构化完成结论,验证结果和依据状态.
- “已独立审查”要求确有另一个获授权且上下文独立的执行方完成复核.
- 未获监控授权时只报告创建与交接状态,不得报告推断的后续进度.
