# 承载路由

本文件是 Skill 触发后的承载路由真源.先选择承载方式;模型选择不得反向改变承载或增加工作单元.

## 承载优先级

按以下顺序匹配,命中更高优先级后不要被后续通用词覆盖:

1. 用户只要求规划或拆分建议:只返回方案,不创建任何承载对象,不加载派发任务包或场景生命周期.
2. 用户明确要求内部子代理与用户侧新任务混合承载,包括为不同工作明确指定两种承载:进入 `mixed-carriers.md`,先划分哪一层采用哪种承载方式,再派发.不能因同句包含“新任务”或“子代理”而退回单一承载.
3. 用户明确要求新任务,新线程,新聊天或侧栏任务:选择用户侧新任务,不得改用内部子代理.即使同一句还包含“拆分”或“并行”,明确新任务仍优先.
4. 用户明确要求子 agent,子代理,内部代理,并行代理或当前任务统一收口:选择内部子代理.
5. 用户只说担任总控,编排,拆分,并行,分工,多任务处理或减少主控上下文污染,没有指定承载方式:默认内部子代理,不得因此创建用户侧新任务.
6. 歧义若会新增侧栏任务,超出宿主已定义规则创建工作树,改变目录或分支,产生外部副作用,或改变用户后续跟进方式:询问一个最小必要问题.其他歧义采用影响最小且最贴近用户原话的解释.

用户只要求展示三个任务的拆分方案时按第 1 条路由,不创建任务.“拆成三个新任务”按第 3 条路由,不能被第 5 条覆盖.

回调是承载确定后的条件,不是竞争路由.用户要求主任务先 `FINAL`,完成后再通知时,必须已有用户侧新任务授权,再读取 `new-task-callbacks.md`.尚未授权新任务时先确认,不得从“稍后通知”推断可创建.内部子代理不能使用回调路径.

## 路由后的公共检查

- 只并行真正独立的工作.先列前置依赖和文件/状态所有权;所有权重叠时串行化.
- 任务数量不是并行数量.并发由独立性,槽位,工具 schema 和用户约束决定,不为模型分级增加代理层.
- 创建用户侧任务不等于授权递归委派,持续监控,取消或回调.宿主明确要求的初始状态等待属于创建交接流程,不等于持续监控.
- 用户侧新任务的 `local` 或 `worktree` 是执行环境,不是承载方式.严格串行共享状态时的环境门禁由 [用户侧新任务场景](new-tasks.md#工作目录与串行-checkpoint) 唯一规定;其他场景按用户要求和宿主工具规则决定,不得把该门禁扩成全局 `worktree` 禁令.
- 用户在派发前改变承载方式时停止旧方案并重新排程.派发后按主文件公用失败与恢复原则处理,不得复制在途写任务.
- 简单任务不得仅因为模型路由而扩展成多代理工作流.承载对象数量只由用户要求和明确隔离收益决定.

## 模型与角色边界

- 默认省略模型与 reasoning 覆盖,继承宿主设置.用户已指定有效值时按用户值和当前工具契约执行;用户值被拒绝时报告 `refused`,不静默替换.工具无对应参数时报告 `omitted` 或 `refused`,保持原承载.
- 只有用户要求推荐或分配模型,且宿主允许覆盖时,按主文件路由读取模型选择指导.工具 schema 声明可用性,不构成自动覆盖授权.
- 普通内部执行方是叶子.只有任务包明确授权分支协调,列明后代范围,槽位,所有权和收口责任时才允许有界递归;建议模型等级不授予该权限.
- 内部子代理与用户侧任务即使采用同一模型仍是不同承载,不能合并其生命周期或跟进方式.
