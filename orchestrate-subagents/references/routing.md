# 承载与模型路由

本文件是 Skill 触发后的唯一路由真源.先选择承载方式,再选择模型与 reasoning.模型选择不得反向改变承载方式.

## 承载优先级

按以下顺序匹配,命中更高优先级后不要被后续通用词覆盖:

1. 用户只要求规划或拆分建议:只返回方案,不创建任何承载对象.
2. 用户明确要求新任务,新线程,新聊天或侧栏任务:选择用户侧新任务,不得改用内部子代理.即使同一句还包含“拆分”或“并行”,明确新任务仍优先.
3. 用户明确要求子 agent,子代理,内部代理,并行代理或当前任务统一收口:选择内部子代理.
4. 用户明确要求混合承载:进入 `mixed-carriers.md`,先划分哪一层采用哪种承载方式,再派发.
5. 用户要求主任务先 `FINAL`,完成后再通知:必须先命中用户侧新任务路径,再进入 `new-task-callbacks.md`.不得把回调当作默认节省 token 模式,内部子代理也不得使用此路径.
6. 用户只说担任总控,编排,拆分,并行,分工,多任务处理或减少主控上下文污染,没有指定承载方式:默认内部子代理,不得因此创建用户侧新任务.
7. 歧义若会新增侧栏任务,隐式创建工作树,改变目录或分支,产生外部副作用,或改变用户后续跟进方式:询问一个最小必要问题.
8. 其他歧义:采用影响最小且最贴近用户原话的解释.

“拆成三个新任务”同时包含拆分与新任务时按第 2 条路由,不能被第 6 条覆盖.用户只要求展示三个任务的拆分方案时按第 1 条路由,不创建任务.

## 路由后的公共检查

- 只并行真正独立的工作.先列前置依赖和文件/状态所有权;所有权重叠时串行化.
- 任务数量不是并行数量.并发只受独立性,槽位,工具 schema 和用户约束决定.
- 创建用户侧任务不等于授权新建工作树,递归委派,监控,取消或回调.
- 用户在派发前改变承载方式时停止旧方案并重新排程.派发后按主文件的公用失败与恢复原则处理,不得复制在途写任务.
- 简单任务不得仅因为模型路由而扩展成多代理工作流.承载对象的数量只由用户要求和明确的隔离收益决定.

## 模型与 reasoning 第二层路由

按以下优先级解析每个已确定承载方式的工作单元:

1. 用户明确指定且当前工具 schema 支持的模型与 reasoning.用户显式选择不得被建议路由覆盖,也不要求先出现在本 Skill 的映射数据中.
2. 当前工具 schema 实际支持的模型和 reasoning 参数.映射数据不得声明运行时可用性.
3. 下方通用等级,任务画像与最低足够 reasoning 原则.
4. 不支持隐式覆盖或没有可靠映射时写 `omitted`;用户明确值无效或被工具拒绝时写 `refused`,并保留原承载方式.

等级表示完成当前工作所需的最低协调与判断能力,不是产品排名,价格排序或绝对质量评价.高等级模型通常也能完成低等级任务,但不得因此默认选用更高等级.

### 通用等级

- `L4`:战略总控.适合根级目标解释,跨分支决策,架构与协议边界,授权边界,重大歧义,高风险升级和最终验收.只用于当前根主控或获授权的用户侧独立根任务,不得把普通叶子提升到此等级.
- `L3`:协作分支.适合分支自身确实需要协调其他代理,递归委派,整合多个依赖结果,复杂审查或较强中间判断的任务.只有任务包明确给出后代边界和递归授权时才能继续委派.
- `L2`:聚焦代码.适合范围清楚但仍需要代码理解与快速编辑验证循环的终端任务,包括只读代码探索,已理解故障后的目标修复,小型重构,聚焦测试和细粒度界面迭代.默认不得递归委派.
- `L1`:边界吞吐.适合明确,独立,可重复,高吞吐且可客观验证的终端任务,包括资料或日志扫描,文档研究,代码映射,固定规则检查和重复验证.默认不得递归委派.

等级不是固定流水线.`L3` 只服务需要协调的分支,不是 `L4` 与叶子任务之间的必经中间层.`L1` 与 `L2` 都是终端等级;前者偏重复与吞吐,后者偏聚焦代码判断和编辑验证循环.

### 通用任务画像

先为工作单元选择一个主要画像,必要时补充一个次要画像:

- `strategic-control`:根级目标,授权,风险与最终收口.
- `cross-branch-decision`:跨分支冲突,依赖与架构决策.
- `branch-coordination`:协调后代,维护分支依赖并整合结果.
- `dependency-integration`:整合多个独立来源或执行结果.
- `complex-review`:需要较强判断的代码,协议,安全或质量审查.
- `browser-debugging`:需要观察,定位与验证闭环的浏览器问题.
- `read-only-code-exploration`:固定问题下的只读源码探索.
- `targeted-code-change`:原因或目标已清楚的小范围修改与测试.
- `focused-refactor-test`:边界明确的小型重构和聚焦验证.
- `granular-ui-iteration`:既有应用中的快速,细粒度界面修改.
- `bounded-scan`:固定范围的资料,日志或结构化结果扫描.
- `documentation-research`:边界明确的文档检索与归纳.
- `code-mapping`:只读梳理代码位置,关系与所有权.
- `repeatable-validation`:固定命令或规则下的重复验证.
- `high-volume-clear-work`:输入输出明确的高吞吐独立工作.

### 具体模型解析

只有需要隐式选择具体模型时,才使用主文件直接声明的模型映射 JSON:

1. 根据任务的协调深度,判断强度和编辑闭环选择最低足够等级.
2. 选择主要任务画像,并检查是否需要一个次要画像消除歧义.
3. 在 JSON 中只保留等级与画像匹配,且当前工具 schema 实际支持的候选.映射中的具体名称只属于数据,不得复制回 Markdown,metadata 或任务模板.
4. 多个候选都满足时,选择任务画像更接近且 reasoning 要求最低的候选.没有可靠差异时不猜测,写 `omitted`.
5. 用户显式指定且工具支持的未映射模型仍按用户值执行;JSON 不是允许列表.

reasoning profile 使用 `light`,`balanced`,`deep`,`exceptional` 四个通用值.`light` 用于机械且低风险的重复工作;`balanced` 用于常规代码理解,修改和验证;`deep` 用于复杂逻辑,边界检查,协调或高风险审查;`exceptional` 只在工具支持且任务证明确有必要时使用.运行时选择满足质量门槛的最低支持 effort,不得默认使用最高模型或最高 reasoning.

## 约束

- 当前客户端的用户模型选择和工具 schema 高于本 Skill 建议.不得修改用户选择,私有 model catalog,隐藏 feature flag 或兼容补丁.
- 模型映射是可替换数据,不是运行时能力声明.具体模型只有出现在当前工具 schema 中才能被隐式选择.
- 工具不支持模型覆盖时,不得通过改换承载方式,创建额外任务或增加代理来规避.
- `L1` 与 `L2` 默认是终端叶子.`L3` 只有任务包明确授权分支协调和后代边界时才能继续委派.
- 内部子代理和用户侧独立任务即使采用同一等级或模型,仍是不同承载方式.模型相同不代表生命周期,所有权或跟进方式相同.
