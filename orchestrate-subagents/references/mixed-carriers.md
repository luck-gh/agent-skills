# 混合承载生命周期

只在 `routing.md` 已确认用户明确要求内部子代理与用户侧新任务共同承载时使用本文件.先规划层,再为每层读取对应场景 reference.

## PLAN_LAYERS

派发前建立最小分层表,每层只记录:

- 工作单元和独立成果.
- 承载方式及选择依据.
- 前置依赖与跨层交付.
- 文件/状态所有权.
- 模型与 reasoning 显式值,建议理由,或 `omitted` / `refused`.
- 是否属于最终必需完成集合.
- 用户直接跟进或根主控统一收口.
- 主控保持 `WAITING` 或获准先 `FINAL`.
- 回调发送方与收集者;不使用回调时写“不适用”.

内部子代理适合同一主任务中需要统一收口的临时,有界工作.用户侧新任务适合用户需要在侧栏独立查看,持续跟进或保留独立上下文的成果.模型相同不能合并两种承载方式.

## 依赖与所有权

- 先解析跨层依赖.依赖未满足的工作保持待派发,不得用推测结果启动.
- 一个文件或外部状态在任一时刻只有一个写所有者.跨层所有权重叠时串行化,并写明交接状态.
- 用户侧任务交付给内部子代理时,必须提供新鲜的结构化结果及依据状态;不得让内部子代理读取完整远端历史.
- 内部结果交付给用户侧任务时,只传必要摘要,证据和已满足依赖,不得暴露其他分支讨论.

## 生命周期

```text
PLAN_LAYERS
-> DISPATCH_INTERNAL / CREATE_USER_TASKS
-> WAITING
-> ALL_REQUIRED_RETURNED
-> COLLECT_ONCE
-> FINAL
```

允许的旁路状态:

```text
WAITING -> NEEDS_USER -> WAITING
WAITING -> REPLAN -> DISPATCH_INTERNAL / CREATE_USER_TASKS
WAITING -> BLOCKED
WAITING -> CANCELLED
WAITING -> UNKNOWN
```

1. 在 `PLAN_LAYERS` 明确每层承载,依赖,所有权,最终完成集合和用户跟进方式.
2. 只派发已满足依赖的层.可并行的内部与用户侧工作必须同时满足所有权互斥.
3. 默认主控保持 `WAITING`,使用各承载场景的事件机制收集状态.不要让用户侧任务和内部子代理分别驱动多次汇总.
4. 用户要求分别跟进时,用户侧任务可交接给用户,但必须明确它们是否仍属于当前主控的最终完成集合.
5. 所有必需结果齐备后只进入一次 `COLLECT_ONCE`,统一处理冲突,验证证据,取消项和未知项.

## 主任务先 FINAL

只有用户侧任务可以在主任务 `FINAL` 后进入 callback 路径.内部子代理不能依赖主任务结束后回传.

若用户要求主任务先结束:

- 尚未派发的内部工作必须改为用户侧任务,删除出完成集合,或由用户选择其他处理方式.
- 已派发的内部工作不得静默迁移.等待其在主任务结束前完成,经授权取消,或向用户报告无法先 `FINAL` 的冲突.
- 多个用户侧任务优先由一个收集者发送一次回调.回调发送方必须在 `PLAN_LAYERS` 中唯一确定.
- 不得让多个任务无控制地分别唤醒主控.无法在用户授权数量内指定收集者时请求用户选择.

## 失败,恢复与承载变更

- 每层按主文件公用失败原则和自身场景状态协议处理.瞬时失败不改变承载方式,验证失败仍返回原所有者.
- 用户在派发前改变承载方式时进入 `REPLAN`,停止旧方案并重新排程未派发工作.
- 用户在派发后改变承载方式时,不得静默迁移,复制或重启在途工作.只有用户明确授权且工具支持时才能取消;否则等待完成,明确弃用结果,或报告所有权冲突.
- 状态不明时只做一次紧凑检查并进入 `BLOCKED` 或 `UNKNOWN`.不得派发可能重复写入的替代工作.
- `CANCELLED`,`BLOCKED` 和 `UNKNOWN` 是否阻止最终完成,由 `PLAN_LAYERS` 中的必需完成集合决定,不得事后降低验收标准.
