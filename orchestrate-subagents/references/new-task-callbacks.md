# 新任务完成后回调

只在用户明确要求主任务先 `FINAL`,待用户侧新任务完成后再通知时使用本文件.内部子代理不得使用此路径.读取本文件前必须已按主文件入口确认用户侧新任务契约.

## 能力与授权检查

创建任务前确认:

- 当前工具能获得准确的主任务 ID,并支持用户侧任务向该现有任务发送消息.
- 主任务可在 `FINAL` 后接收消息并开启新 turn,没有被删除或置于无法继续的状态.
- 用户明确要求主任务先 `FINAL`,而不是保持事件 `WAITING`.
- 用户理解回调可能重新载入上下文并增加 token.
- 任务包能写入稳定且唯一的 `batch_id`,`task_id` 和总任务数.

任一能力条件不满足时,不得承诺自动回传.让用户选择根主控事件等待,或仅创建并交接.

## 单个新任务

单个任务完成后只尽力发送一次紧凑回调.回调发送本身的重试预算为 0,避免未知发送状态下重复唤醒.接收方仍必须去重.

回调包含:

- `batch_id`,`task_id` 和总任务数.
- 最终状态与结论.
- 修改文件或状态.
- 验证命令,退出码与结果.
- 结果新鲜度或依据状态.
- 遗留风险或需要用户决定的事项.

不要发送原始日志,完整任务历史或逐步调试过程.

## 多个新任务

不得让多个任务无控制地分别唤醒主控.优先使用单一收集者:

1. 在用户已授权的任务数量内指定一个收集者.其他任务只把结构化结果发给收集者.
2. 收集者按 `batch_id` 和 `task_id` 去重,维护必需完成集合,并等待所有必需结果.
3. 结果齐备后,收集者只向主任务发送一次汇总回调,使主控只唤醒一次.
4. 无法在授权数量内安排收集者时,先让用户选择:授权增加一个收集任务,接受多次唤醒,改为主控事件等待,或仅创建并交接.

不得擅自增加收集任务数量,改变用户指定的任务数量,或创建多级收集树.

## 重复,迟到和不完整回调

- 重复:接收方以 `(batch_id,task_id)` 为键忽略已处理结果.重复消息不得再次计入完成集合或触发第二次汇总.
- 迟到:收集者已经发送最终汇总后到达的结果不得触发第二次回调.保留其状态供用户后续查询,并明确它未进入先前完成集合.
- 不完整:向原发送任务请求一次最小缺失项,不要重读完整历史.仍不完整时标记 `BLOCKED` 或 `UNKNOWN`,并按必需完成集合决定是否能汇总.
- 发送状态不明:发送方不得再次发送.接收方若收到重复消息仍按标识去重.

## 状态协议

```text
CREATE -> MAIN_FINAL -> WORKERS_RETURN_TO_COLLECTOR -> ALL_REQUIRED_RETURNED -> ONE_CALLBACK -> NEW_MAIN_TURN
WORKERS_RETURN_TO_COLLECTOR -> NEEDS_USER -> WORKERS_RETURN_TO_COLLECTOR
WORKERS_RETURN_TO_COLLECTOR -> BLOCKED
WORKERS_RETURN_TO_COLLECTOR -> CANCELLED
WORKERS_RETURN_TO_COLLECTOR -> UNKNOWN
```

新主 turn 只依据回调摘要和标识处理结果.信息不全时只请求缺失项,不要重新读取全部任务历史.
