# orchestrate-subagents

在显式调用后让当前主任务担任纯总控,把可独立验收的工作交给执行方,协调依赖,所有权,等待与结果验收.适合有清晰分工的多步骤工作,也支持用户明确要求的独立任务或混合承载.

主控负责组织和决策,执行方负责其范围内的研究,修改与验证.普通请求或讨论本 Skill 用法不会启动编排;无法划分独立成果时不应为了并行拆碎任务.

## 安装与显式调用

从[公共仓库](https://github.com/luck-gh/agent-skills)取得完整 `orchestrate-subagents/`.当前工作区未发布内容可直接接入,公共下载只包含已发布版本.

Codex 用户级目录为 `$HOME/.agents/skills`,Windows 为 `%USERPROFILE%\.agents\skills`.将完整实体目录安装于其下,或创建精确指向唯一实体的目录链接,不覆盖已有目标.其他宿主以其发现契约为准.发现机制见 [Codex 官方文档](https://developers.openai.com/codex/skills#where-codex-loads-local-skills).

本 Skill 设置为仅显式调用.安装后使用 `$orchestrate-subagents`,不要以未自动触发判断安装失败;列表未刷新时重启 Agent.使用无需 settings 或 Python 包,但实际派发需要宿主提供相应协作工具和权限.

## 最小示例

```text
使用 $orchestrate-subagents,用内部子代理完成两个独立只读成果:一份审查当前接口文档的输入约束,另一份审查用户手册的错误恢复说明.各自输出问题与证据,主控汇总冲突和未验证项.不要修改文件或新建侧栏任务.
```

进阶用例:

```text
使用 $orchestrate-subagents,将当前已确认的改动拆成实现与验收单元.先按文件所有权安排实施,依赖项完成后再审查.内部子代理使用你按任务选择的可用模型,主任务保持当前模型.不提交、不推送;结果未知时先核实,不要派新执行方重复写入.
```

如果明确希望产生用户侧独立任务,在请求中说明任务与项目;仅调用本 Skill 不自动授权创建侧栏任务,也不默认创建后台回调.

## 输入与工作方式

输入是总体成果,原始需求,可读写范围,当前任务状态,依赖与验收标准.调用后自动按工作单元选择最低足够能力,无需重复提醒选模或节省资源;新增独立成果时重新评估,不因已有代理使用强模型而一直沿用.同一问题的修复与验证保留原所有者闭环,避免为换模反复交接.用户指定模型或要求继承时优先遵从.自动选模依据实际工具 schema 与[模型选择指导](references/model-selection.md),具体候选由[模型映射](references/model-routing.json)维护,不会在 README 再维护一套名单.

主控只读取必要指令,建立互斥所有权与任务包,再按[承载路由](references/routing.md)选择内部子代理,用户侧任务或混合方式.执行方返回精简成果和证据,主控统一等待,处理冲突并验收.领域工作由执行方读取适用 Skill;涉及 Skill 修改的任务还需生命周期入口,不能由主控接管修复.

输出包括实际承载,完成集合,改动与验证结果,未知/取消状态及需决策项.用户中途改变安排时先处理在途工作,不会静默复制执行.超时不等于失败,缺工具或权限也不是升级模型的理由.

## 常见问题与验证边界

- 主控为什么不顺手修复小问题?纯总控职责要求把具体执行保留给拥有该范围的执行方.
- 请求的模型是否真的运行了?只有工具回显才能确认;未回显时报告请求参数,不冒充后台实际值.
- 支持任意宿主或无限递归吗?不支持.参数,继承,并发与回调受当前工具契约约束,不能制造兼容参数或绕过权限.
- 能保证降低成本吗?不能.规则要求综合考虑执行,上下文,协调和返工成本,高等级选模须有具体依据,收口时检查无依据沿用及重复工作.已有有限模拟对照和两个教学样例来自本次成本规则修订前;新增复评与交接规则尚未进行独立模型行为验证,没有普遍 Token/成本收益实测,也未覆盖全部模型或写任务交接.
