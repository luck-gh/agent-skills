# 新 Codex 任务

仅在用户明确选择委派新负责人,拆成多个 Codex 任务,新整合任务或 GOAL 接力时读取.普通显式调用默认当前任务拆给内部子 Agent,不进入本分支.单纯允许按需创建任务不要求创建,实际创建仍须满足宿主的人类明确授权.遵守用户指定的数量,标题,项目,环境与模型,不额外建立管理/收集/审查聊天,不逐项重问已有授权.

- 委派完整成果:默认创建一个负责人,新负责人默认拆给内部子 Agent;用户明确“委派后不拆分”时新负责人独立完成.
- 直接拆成多个 Codex 任务:按大型独立成果和明确所有权分工,当前任务仍是执行负责人,拥有协调,最终验证和整合责任.不再额外创建一个只负责转发的委派任务.
- 委派后再拆成 Codex 任务:必须由用户明确选择并授权负责人创建一层执行聊天,固定总数量/层级和消息路径.下级只能按授权使用内部 Agent,不能继续创建侧栏任务;迭代唯一后继另按专用契约处理.

## 创建与状态

1. 按宿主要求查询已保存项目,核对工具支持的环境与参数.创建权限不附带消息,持续监控,取消,归档或 Git 权限;已授权本批回传和必要验收反馈时可沿用,不重复问.默认内部拆分不能推导侧栏创建权,用户明确不拆分时两种承载都关闭.委派后侧栏拆分只允许上文明确授权的一层,GOAL 唯一后继由专用契约授权.
2. 用户侧模型覆盖严格按工具条件.若要求用户指定具体模型,仅调用 Skill 或说自动选模不足以覆盖,须省略参数;reasoning 同样检查.不支持的请求报告 omitted/refused,不静默替换,不通过后续消息绕过.内部自动选模权限不适用于这里.
3. 用下方独立可执行的任务包创建,不复制父聊天.GOAL 首轮与后继用其固定契约,仅递增编号,不传动态摘要.用户已选择侧栏承载时仅用用户侧创建工具,不因失败改为内部子 Agent.
4. 创建异步返回后,保存原标识并完成宿主要求的有界初始状态核验.使用有效 threadId,host 和 cursor;只有 clientThreadId 时先紧凑查询,未取得真实 ID 不用于等待或重建.已创建/运行/完成分别按实际证据报告,创建不等于交付.
5. 创建失败或结果未知停止依赖派发,核查原请求;未知时不重建,不改承载或递增编号.成功时返回宿主要求的可识别入口,说明目标及跟进方式.

## 工作目录与串行 checkpoint

sandbox 权限不决定工作目录,也不保证多个任务共享状态.按宿主默认环境及用户要求选择,不自行新增分支或工作树.

需要后轮继承同一可变仓库时,固定同一已保存项目 ID 和 `environment: { type: "local" }`.只有用户明确要求隔离并已明确状态继承/整合方案与授权时才使用 worktree;不把这个特例扩为全局禁令.

- **依赖工作或整合任务**:前序任务必须已结束且所有权释放.前序返回实际目录,改动路径,branch,HEAD 和 `git status --short --branch` 摘要;无提交授权时指明未提交成果及其可核验候选,不擅自提交来制造版本.非 Git 目录明确说明.前序仍运行,等审批,重试或状态未知时不派后序写者.目录/证据/所有权冲突先核实.
- **GOAL 自接力**:按 `goal-relay.md` 的验收提交,写者结束及仓库冻结交接,前轮可尚未 FINAL.后继自己读取仓库状态,不携带前序动态 Git 摘要.

## 跟进方式

- 仅创建并交接:初始核验后报告已观察状态并结束,不持续读取或推测进度.
- 侧栏默认完成后回传:派发前核验接收方及消息路径;完成必要初始状态核验且没有内部在途工作时可先结束接收任务回合.仅余侧栏结果的执行负责人须在回传后恢复自己的整合职责,不能提前向上级宣称完成.多任务分别回所属负责人,不因部分结果介入正常实施.
- 用户明确保持等待:用紧凑事件等待接收必需结果,有活跃证据的 timeout 继续等,不能复制写者.等待不意味着持续查看源码/长日志或发送“继续”;中途协调只限主入口列出的例外.
- GOAL:创建唯一后继并完成初始核验即退出,不驻留逐轮协调.

## 普通执行任务启动模板

```text
你是本成果的执行负责人,按 $orchestrate-tasks 的已选分支和共同规则执行.
角色与分支:<完整成果受委派负责人,或拆分后的 Codex 执行任务>;拆分选择:<默认内部 Agent,明确不拆分,或明确授权的一层 Codex 执行聊天>.
目标与完整成果:<内容>.输入及路径/前置依赖:<已就绪的资料和候选版本>.
范围/非目标:<内容>.文件,资源和共享文档所有权:<唯一写者与交付边界>.
授权:<写入,内部子 Agent,Git,设备与消息各自的真实授权及来源>.
验收标准/停止条件:<内容>.项目,环境及用户模型选择:<内容>.
自主完成调查,实施,拆分协调,自查,验证,范围内修复与必要文档收口.默认评估并实施合理内部拆分,没有合理拆分点说明原因,明确不拆分则独立完成.
只创建用户明确授权层级和数量的执行任务,不把内部协调或文档责任交回上级.
所属负责人/结果接收任务/批次标识:<宿主已有准确标识>;原主任务:<与所属负责人不同才另列>.本批必要成果集合:<内容>.
交付方式:<已核验的回传路径,或用户选择的等待/仅交接>.
已选回传时,完成后按回调规则向指定接收任务发送一次紧凑结果;等待或仅交接按已选方式交付,不额外发送未获授权的消息.下级结果先向你交付,由你整合后再向上级统一返回.
只有用户变更/暂停,无法自主解决的阻塞或授权缺口,有证据的越界/冲突/设备风险才中途协调.
```

只填本次必要字段,模板不产生授权.当前任务执行时使用相同职责和验收要求,省略创建与外部回调字段.最终报告区分实际执行,审查,取消及未知结果,不将请求模型写成已确认模型.

## 整合任务

当前任务作为执行负责人时,默认自行完成本批整合,不因拆分就新建整合任务.用户明确选择新整合任务,或纯总控处理多个独立成果且已有明确批次授权覆盖整合时,才沿用本节.先判断是否需要合并,联调或组合验证,仅汇总结论则直接验收.确需新整合负责人时复用普通模板,补齐前序成果/版本,写者结束依据,最终组合验收和共享文档所有权.纯总控缺此授权时只补缺口,不代改代码.

整合负责人合并成果,处理集成问题,针对最终候选验证和自查,完成共享文档收口后统一回传.验收问题集中交回原整合负责人;不能用某个分项测试或任务创建成功代替整体交付.
