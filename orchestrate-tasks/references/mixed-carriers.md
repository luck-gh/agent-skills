# 混合承载

仅在用户明确选择多个侧栏执行任务与内部子 Agent 组合,或委派后再拆成 Codex 任务时读取.默认当前任务内部拆分不加载本分支.混合承载是执行安排,不自行增加委派层级或常驻总控.GOAL 轮内使用子 Agent 不改变唯一轮次负责人和串行接力.

1. 用最小表列工作成果,承载,依赖,文件/状态所有权,必需完成集合及跟进方式.各层分别遵守工具的模型与消息权限,同一模型不代表同一承载.
2. 只派发输入就绪且无写入冲突的工作,分别读取主入口链接的内部/新任务说明.跨层交付只传必要结果,证据和依据状态,不读完整聊天.共享 Git 操作仍由唯一所有者负责.
3. 各执行方自主协调自己的内部 Agent,收齐并验证后按已选方式向所属负责人交付.直接拆分时所属负责人是当前任务;委派后再拆分时是受委派负责人,由其整合后统一回原主任务.不让下级分别唤醒原主任务,也不把协调责任交回纯总控.原任务只有在不持有内部在途工作且已核验侧栏交付路径时才可先结束回合.创建/状态未知停止依赖层,不改承载重派或事后降低完成标准.
4. 用户改变方案时只重排未派发工作.在途工作不能静默迁移或复制,取消须授权;否则等待完成或报告所有权冲突.
5. 持有内部 Agent 的执行负责人结束前须收齐其必需结果或按授权处理,不能假设内部 Agent 随后回调.尚未派发的工作只有用户明确选定侧栏承载且获准创建时才可改新聊天.多个侧栏执行方按回调规则分别反馈所属负责人,不强制增加收集者.必要成果就绪且写者结束后由执行负责人整合,另建整合任务必须属于显式分支及其授权,独立结论直接验收.

例如用户明确把独立模块 A/B 拆成两个 Codex 任务,各自默认评估合理的内部拆分.A 的助手只交付 A 负责人,B 同理,A/B 再交当前负责人统一整合.若用户明确先委派 E 再允许 E 创建 A/B,则 A/B 只向 E 交付,E 统一回原主任务;A/B 无权继续创建侧栏任务.所有创建及消息路径分别核验真实人类授权.共享文档和 Git 仍由指定单写者维护;若 B 依赖 A 的接口候选,先取得该明确版本再启动 B 的依赖工作,不靠持续聊天补齐缺失输入.
