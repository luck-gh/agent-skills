# 任务编排与迭代接力

先与用户明确目标,边界,授权和验收要求.默认当前任务就是执行负责人,把有意义的独立成果拆给内部子 Agent,自行负责协调,整合,自查,最终验证及必要文档收口.子 Agent 自主完成所分配成果的调查,实施,验证和范围内修复.复用上下文和已有明确授权,只补问必要缺口,不要求用户填派发模板.

## 选择流程与承载

- 未要求执行编排时不主动派发;仅讨论,解释方案或要求不要派发时到讨论为止.修改本 Skill 不等于执行其中的业务编排.
- **默认直接拆分**:显式调用执行编排且没有其他明确选择时,当前任务担任负责人,拆给内部子 Agent,完成一次交付.不先创建委派任务,不自动建立侧栏聊天或 GOAL 接力.
- **委派**决定谁承担完整交付责任,**拆分**决定负责人如何组织执行,两者可独立选择或组合.委派不再吞并直接拆分入口,也不把执行位置,承载和迭代混成互斥模式.
- **一次性交互**是一个有界交付批次:一次说明完整工作包,执行方自主闭环后交付,负责人收齐并统一验收.同批依赖推进,必要修复和验证不因此省略,但不自动续轮,创建后继或启动持续优化循环,不反复发送“继续”.
- 已明确的负责人,拆分选择,承载和推进方式跨用户回合沿用,不因“继续”或省略选择重置.默认值只补尚未选择的项.

负责人默认实施有实际收益的拆分,不能仅因为自己也能完成就跳过.按独立成果,输入就绪和所有权决定拆分,不为凑数量制造工作;很小,强串行或无法划清写入范围的任务没有合理拆分点时,简短说明具体原因后直接完成.用户明确“不拆分”时关闭内部和侧栏拆分,负责人独立完成,不能改用另一种助手绕过选择.

| 用户明确选择的分支 | 执行与读取 |
| --- | --- |
| 委派给新 Codex 任务 | 创建一个完整成果负责人,原任务成为纯总控;受委派负责人默认拆给内部子 Agent,无需用户再次要求拆分 |
| 委派,不要拆分 | 新负责人直接完成完整成果,不创建子 Agent 或下级执行聊天 |
| 拆成多个 Codex 任务 | 按大型独立成果,输入就绪和明确所有权分工;当前负责人仍承担协调与整合责任,不因工作量大自行启用 |
| 委派后拆成多个 Codex 任务 | 原任务委派一个负责人,该负责人仅在用户明确数量/层级授权内创建一层执行聊天,不继续递归建立侧栏树 |
| 迭代或 GOAL 接力 | 读取 [GOAL 接力](references/goal-relay.md),按目标,验收和停止条件推进;该分支默认每轮新建任务,可明确指定当前任务为首轮负责人,仍受后继授权门禁约束 |

分支必须来自用户明确选择,一次“允许按需创建任务”只提供权限,不意味着必须偏离默认内部拆分.显式执行本 Skill 已表达所选分支的默认内部拆分意图;宿主允许由用户或 Skill 请求内部协作时直接执行,不额外要求用户再说一次“允许子 Agent”.宿主更严格的授权条件仍须满足,实际侧栏创建,跨任务消息,Git 或设备权限不能从默认值推导.已有明确授权复用,不逐项再问.不擅自创建 worktree,扩大任务数量或侧栏层级.多任务拆分不能创建并行迭代轮次或下放唯一后继权.

## 角色与共同边界

- **纯总控**:显式委派完整成果后,原任务沟通目标,派发,接收结果和最终验收.只读必要指令与紧凑交付证据,不代做源码调查,项目修改,领域测试或复验.验收问题集中反馈对应负责人,不逐步指导或亲自代改.此限制不施加给默认的当前执行负责人.
- **执行负责人**:负责调查,修改,拆分协调,自查,验证,整合及文档收口.默认是当前任务,显式委派后是新负责人,迭代时是该轮负责人.可以直接承担自己的工作及最终集成,不能因为叫“主任务”就放弃实施和整合.被派发后直接履行所分配责任,不再把整个成果转交另一个中转负责人.内部子 Agent 先向所属负责人交付,不分别唤醒原主任务.
- 只派发输入就绪且所有权明确的工作.同一文件,外部资源及同一工作树的 Git index/commit 只能有一个写者;目录不同不代表 Git 独立.并发同时考虑槽位和未收口结果,依赖未满足或决策积压时先等待.
- 有依赖的工作等待明确成果或源码版本后再执行,不靠频繁消息弥补输入未就绪.共享文档也保持单写者,各执行方提供范围内事实和证据,由指定负责人收口.
- 保留用户已有修改和 staged 内容.提交,推送,发布,消息,取消等动作分别遵守有效授权及宿主规则;不擅自改目录或创建 worktree.调用 Skill 不撤销“先不提交”等限制.

## 最小派发与按需读取

任务包一次说明目标与成果,输入及精确路径,依赖,范围与非目标,文件/资源及共享文档所有权,授权,验收和停止条件.明确本批必要结果集合,用宿主已有批次/任务标识区分交付,不新建状态框架.领域 Skill 给入口并由执行方完整读取;写 Skill 先遵循可用的 $new-skills 生命周期契约.长材料传路径和读取目的,不复制整段聊天或日志.

- 派发内部执行方时读 [子 Agent](references/subagents.md).
- 创建用户侧聊天或整合任务时读 [新 Codex 任务](references/new-tasks.md);GOAL 固定契约替代普通任务包及动态 checkpoint 摘要.
- 明确使用多个侧栏负责人及内部子 Agent,或委派后再拆成 Codex 任务时读 [混合承载](references/mixed-carriers.md),固定各级责任与结果返回路径.
- 自动选择内部模型或复评能力时读 [模型选择](references/model-selection.md) 与 [模型 JSON](references/model-routing.json).具体模型名称只在 JSON 维护;用户已指定有效值或要求继承时不加载选型材料.当前主任务不换模,用户侧任务的覆盖权限按工具另行核对.
- 使用侧栏任务时在派发前读 [完成后回调](references/new-task-callbacks.md),按选定交付方式核验能力和授权.选择回传时核实原主任务准确标识,发送并继续对话的宿主能力及人类用户对消息路径的授权;迭代将这些固定字段传至各轮.用户已选等待或仅交接时不强制回传条件.

不预读其他分支,README 或测试材料.派发时简述承载和选模理由;请求值与工具确认值分开,未回显不能称已确认实际模型.

## 自主执行与交付后处理

默认流程:当前任务明确需求并拆分 -> 内部子 Agent 自主完成,当前负责人可并行处理自己的独立工作 -> 收齐必需结果并完成必要修复,整合,验证和文档 -> 向用户统一交付并结束.有必需内部结果未收齐时不提前结束执行回合,不假设子 Agent 会在结束后唤醒当前任务.需要等待时用事件等待,不持续查看过程,催促或逐步指导.

只有显式侧栏分支才使用“派发并完成必要初始核验后结束 -> 负责人完成后回传 -> 接收任务新回合验收”.持有未完成内部工作时不能提前结束;仅余侧栏结果且已核验回传路径时可先结束回合,但仍保留接收后整合的责任,不能把退出当完成或提前向上级交付.用户明确保持等待时沿用事件等待;宿主不支持回传或缺消息授权时明确限制,不虚构后台唤醒,不静默改高频轮询或新增服务.

只有用户变更要求或暂停,无法自主解决的真实阻塞/授权缺口,以及有证据的越界,覆盖冲突或设备风险允许中途协调.普通实现选择和范围内可解决的编译/测试失败由负责人处理.

- 单个受委派负责人完成后发送紧凑交付.多个 Codex 执行任务可分别直接回传所属负责人,不强制增加收集任务;委派再拆分时,内部结果先归受委派负责人,再由其统一回传原主任务.接收方收到部分结果只记录完成情况和必要问题,不介入正常实施.去重及未知发送处理按回调说明.
- 迭代各轮自主接力,整批达标或必须停止时向原主任务汇总;真正需要主任务解决的阻塞可提前反馈,不逐轮催促或汇报流水.
- 必要成果齐备后,执行负责人在写权归还且版本明确时负责合并,联调或组合验证,默认内部拆分不另建整合聊天.只有用户明确要求或已有明确批次授权覆盖新整合任务时才创建.纯总控不代做集成,将问题集中交原负责人;多个独立侧栏成果确需新整合负责人但缺授权时只补此缺口.未完成,失败或未知依赖不能冒充就绪结果.整合含最终候选验证,自查及共享文档收口;独立结论直接汇总验收.
- 回传包含任务身份,完成/部分/阻塞/取消/未知状态,主要结论,修改范围,实际验证及依据,必要文档位置,未完成项和在途操作.不发送完整聊天,原始长日志或逐步调试过程.

## 共同文档收口

委派,迭代,当前任务执行,内部拆分和最终整合都须在交付前判断并完成必要文档更新.通用文档职责以 `bootstrap-project-context` 的项目文档契约(`references/project-document-contract.md`)及项目已有落实为真源,不在本 Skill 维护另一套定义或每轮重新初始化.按项目路由读取已有真源;确需核对通用契约时只使用用户提供或宿主可用的该 Skill 入口及其引用,缺失则说明,不硬编码兄弟目录依赖或猜造规则.

收口时按职责路由:GOAL 留批次目标,验收,剩余缺口,阻塞与停止边界;PLAN 或既有任务真源留已确认后续计划,依赖和关键决策;FEATURES 留有实现与成功验证的当前主要能力和限制;EXPERIENCE 留经实践证实且可复用的方法.接口,算法,配置,架构和操作方法更新专项真源,修复事实和验证证据更新已有缺陷/变更/证据位置,稳定开发规则,文档路由与验证入口归 AGENTS.这里只规定编排交付时的路由检查,具体进入,合并,退出规则沿通用契约.

- 新功能,旧功能 Bug 修复,性能优化和测试流程改进均检查必要记录,不强制每次修改全部文档.局部已完成修复不自动塞进 PLAN,等效重测不强制刷新 FEATURES;普通委派和内部拆分不强制创建 GOAL.
- Bug 修复的必要事实应能回答出现条件与影响范围,已证实原因或待验证假设,修复方式,实现和回归入口,实际验证状态及剩余限制.复用现有证据位置,不强制每个局部修复新建 Bug 文档.
- 保留影响后续决策的关键失败尝试,适用限制和独有证据;假设,失败及未验证范围不得记录为已证实经验或成功能力.不复制聊天/重复日志,不把所有内容塞入 GOAL,不建重复台账或 handoff 框架.下一迭代轮须能从项目资料与证据接续,不依赖前轮聊天.
- 各执行方提供自己范围的事实与证据,指定负责人维护共享文档;纯总控只验收,不逐项催文档.必要更新在交付前完成,有合法提交授权时按项目规则在提交前收口.文档规则不扩大写入或 Git 权限;只读仍只读,必要但未获准的更新具体列出位置,内容和限制.

## 验收与恢复

1. 从目标反查可观察行为,实际产物,连接关系和当前证据,不能用文档宣称,代码存在或单一测试互相替代.组合产物由指定原实施或整合者在最终候选上验证;并列只读结论不重复复验,纯总控不接管.
2. 按风险启用独立审查,给原始要求与质量标准,不预置诊断或固定最强模型.退回具体问题,证据与修复要求给原负责人;复审核对旧问题及修复影响,同类缺陷定向查相邻实现,无新证据不扩大范围.返工到顶不能强制通过.
3. 瞬时失败由同一所有者最多重试一次;回调发送预算及未知恢复按回调说明,创建结果未知先核查不得重建.内部必需结果等待或用户明确保持等待时,活跃句柄或快照仍证明运行就继续事件等待,timeout 不代表失败;侧栏回传流程不据此持续查询.交付状态或字段缺失时,在相应协作/消息授权内向原执行方核实一次,仍不明则停止依赖派发并报告 UNKNOWN/BLOCKED.
4. 验证失败由原所有者修复.内部工作修复一次后仍有能力不足证据,才可在原执行结束,写入结果明确且完成所有权交接后最多升级一次.缺权限,工具,资料或普通超时不触发升级;必需失败或预算耗尽保留失败状态.
5. 恢复先交叉核对旧任务/写者,Git,产物和验收;已有实现缺收口时只补缺失项,不盲目重做或回滚.用户调整先改未派发部分,在途工作按授权协调,不复制写者;发出停止指令不等于已停止.

全部必需结果齐备后统一汇总修改与证据,未完成/未知项及必要决策.创建成功,执行回合结束或单项测试通过均不能替代完整成果验收.达标或没有有价值的下一项就结束,不凑任务或轮数,不把重复测试和扩写文档当作进展.检查无依据的模型沿用和过量上下文,只改后续安排;没有实际用量不宣称节省比例.
